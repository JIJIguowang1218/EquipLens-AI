# 豆包检索咨询评估：一二阶段、Loop、产品护城河（2026-11-15）

> 输入：外部咨询意见 [`docs/external/2026-11-15-doubao-retrieval-consult.md`](external/2026-11-15-doubao-retrieval-consult.md)（微信转发，四部分：豆包链路 / 型号池与校验 / 泛化与冷启动 / 路线图与 Loop）。
> 本文是**评估**，不是实现决定；结论按“采纳 / 部分采纳 / 不采纳”给出，并附预注册实验。
> 对照基线：三轮全类目 `p8-idmatch-20261114` / `-r2` / `-r3`（交付 269/270、confirmed 41.1%、degraded 58.5%）。

## 0. 结论摘要

1. **方向对、细节要打折**：专家描述的“LLM 语义中枢 + 预索引召回 + 文本初筛 + 多模态校验”与我们的两段式同构；真正有增量的只有**多模态校验**和**预索引图像通道**，其余（查询拆分、优先级池、文本打分）我们已有，且我们的身份匹配比它的打分表更严格。
2. **事实性错误先纠正**：豆包 image 搜索**单次最多 5 条**（不是 20 条）；免费额度 **500 次/月/账号**（与 Global 版共用，不区分 SearchType），按我们一轮约 500 条查询，**免费额度只够约 1 轮实验**；检索接口是**自建 HTTP 接口**，不是“兼容 OpenAI 格式 SDK”；“准确率 95%”“YOLO 定位 95%”均无出处。
3. **最该采纳的三件事**：①把“视觉证据”做成第二证据源（参考图库 + 相似度，只升到 A 级、不替代 E1/E2）；②把豆包/必应作为**召回通道**接入，做 A/B 而不是替换；③把“反馈 → 节点路由”的 session 层建起来（这是多轮交互的正确形态）。
4. **最不该照做的一件事**：让 LLM 凭参数化知识“冷启动生成型号池并直接当候选”。这与我方 T18-assoc 的结论（证据 > 判断）和词表政策冲突；只能把 LLM 知识当**查询种子**，候选必须来自检索结果。
5. **产品判断**：工具本身合理，但**“搜图”不是护城河**；护城河是“可核验的参考库 + 证据链 + 设计分析工作流 + 领域评估数据”。专家列的 5 条护城河里有 3 条是通用的，真正可积累的是数据与工作流。

## 1. 事实核查（先于采纳）

| 专家说法 | 核查结果 | 影响 |
|---|---|---|
| 豆包搜索支持 `SearchType=image` 文搜图 | **属实**（需开通 web 搜索；返回 `ImageResults`，含 Title/SiteName/Url/Image{Url,Width,Height,Shape,BlurDes,Watermark}） | 可接入 |
| “单次最多返回 20 张” | **错误**：image 模式 `Count` **最多 5 条**（web 模式最多 50、默认 10） | 同样目标需要更多 query；QPS 默认 5，实验节奏会变慢 |
| “每月 500 次免费” | **属实**，但**与 Global 版共用、不区分 SearchType**；默认 5 QPS，需工单扩容 | 我们一轮 10 类目约 500 条 query → 免费额度 ≈ 1 轮；三轮实验必须付费 |
| “兼容 OpenAI 格式 SDK” | **不准确**：检索是自建 POST 接口（`open.feedcoopapi.com/search_api/web_search`，Bearer API Key），不是 OpenAI 兼容 | 接入要写一个 provider，不是换 base_url |
| 图片结果带正文/alt | **不准确**：image 结果只有标题、站点、落地页（可能为空）、图片元数据；正文/摘要只在 web 模式 | “文本初筛”只能靠标题，不能靠正文；与我们的实测一致（标题带码率 24.9%） |
| “预索引天然绕过反爬” | **部分属实**：搜索调用无反爬；但图片下载仍走 CDN，落地页仍可能 403/失效 | 我们 13.6% 下载失败、10 个图床拉黑的问题**不会自动消失** |
| “多模态两级校验，准确率 95%” | **无出处**；CLIP 对同品牌近似车型的细粒度区分能力有限；YOLO 只做定位，与“型号准确率”不是一回事 | 必须自己做校准实验，不能按 95% 规划 |
| YOLOv8 可自由使用 | **需注意许可**：Ultralytics YOLOv8 为 AGPL-3.0，商业闭源分发需商业授权；或改用 Apache/MIT 的检测模型 | 商业化前必须处理 |

官方依据：[豆包搜索 Custom 版接口文档](https://docs.volcengine.com/docs/networked-search/networked-search?redirect=1&lang=zh)、[产品计费](https://docs.volcengine.com/docs/networked-search/online-search-product-billing?lang=zh)；价格档位在控制台，未在文档页抓取到具体数字。

## 2. 专家方案逐条评估

### 2.1 第一部分：三级链路（LLM 中枢 / 预索引 / 多模态）

- **LLM 语义中枢**：我们已有（`planning.build_query_plan` + `plan_candidates` 抽取），且我们额外做了**证据约束**（候选必须出自该查询的结果 URL），比“LLM 直接生成关键词”更可靠。
- **预索引召回**：我们用的是 360/百度/必应图片搜索（也是预索引），只是没有豆包。**增量在覆盖率与死链率**，不在架构。
- **文本初筛**：我们已有（E1/E2 + `gate`），且我们的码匹配（`identity.py`）比“90/70/50 分”更可解释。
- **多模态校验**：**这是唯一我们没有的环节**。但注意：我们的 `gate` 已经是 CLIP 零样本“是不是车/部件”，缺的是“是不是这个型号”的**参考图比对**。专家把它说成“标准特征库 + 相似度”，方向正确，难度被低估。

**结论：第一部分“部分采纳”**——不重建链路，只补“视觉型号证据”和“图像通道”。

### 2.2 第二部分：型号池 + 三组查询 + 打分 + 两级校验

| 专家机制 | 我们的现状 | 判断 |
|---|---|---|
| 型号池三优先级（官方命名/行业常用/定制补漏） | 我们用 `slots` + `identity_kind` + `intent_rank`，没有“官方命名优先” | **可借鉴**：把“标题是否含码/官方命名”作为 plan 的优先级特征（低成本） |
| 6 维结构化要素 | 我们 `dimensions`（base/model/environment）+ slots（brand/series/model_code/config） | 已覆盖；可补“约束属性”（整车/排除挂车内饰） |
| 三组查询（精准/泛化/补漏） | 我们的分档 + topup + 条件英文档 | 已覆盖；**补漏组**可加“行业别称/英文”，但要按 A3 条件档开关 |
| 文本打分（90/70-80/50 + 权威 +10） | E1/E2 + tier + 来源权威（vetoed 后解耦） | **部分借鉴**：用于排序，不用于准入；权威分可来自豆包 `AuthInfoLevel` |
| 两级多模态（轻量初筛 + 大模型复核） | 只有 gate（CLIP 零样本） | **值得做**，但第一级应是“参考图 k-NN”，不是 YOLO 识别型号 |
| 输出整合 | DELIVERY + 分析/报告 | 已有；可补“参数结构化” |

**结论：第二部分“部分采纳”**——优先级特征、权威分、两级视觉校验值得试；型号池的“LLM 记忆”不能直接当候选。

### 2.3 第三部分：冷启动 + 动态补全 + 分级校验

- **LLM 知识冷启动**：与 T18-assoc 的教训冲突（“凭记忆列车”不可靠；证据基础设施 > 判断）。**只能作为查询种子**：LLM 提议 5–10 个“可能存在的型号”去搜，搜不到就不进池；`validate_extraction` 已强制 URL 归属，天然安全。
- **检索副产品补全**：我们已经在做（SERP 抽取 + merge + topup），且比“边找图边补型号”更结构化。
- **YOLO 只做定位、不做型号**：**完全同意**，也符合我们不训型号分类器的路线。
- **CLIP 参考库自动入库 + 增量自迭代**：**方向正确**，是唯一能规模化解决“标题无码”的路径；但“高置信度文本自动入库”需要防污染（错图入基准会连锁放大）。
- **分级校验（热门强校验/小众弱校验/极小众纯文本）**：**建议采纳**，与我们 `confirmed/probable/unknown` + `degraded` 天然对齐；可以把 A 级视觉证据也做成分级。
- **“纯文本不能做最终校验”**：**方向同意**，但设计场景对“错型号”零容错，视觉校验的假阳性比漏召回更糟；所以视觉只能**加分/升档**，不能单独确认顶级身份。

**结论：第三部分“部分采纳”**——冷启动只做查询种子；参考库要设入池门槛与人工抽检；分级校验采纳。

### 2.4 第四部分：路线图 / Loop / 豆包 API / YOLO+CLIP

- 路线图（MVP→反馈闭环→设计分析）与我们的路线基本一致，但我们的阶段划分应是“先证据与工作流，再视觉增强”，不是“先视觉”。
- Loop 设计见 §4（这是本文重点）。
- 豆包 API 见 §1；可作为新通道，但不能替代现有三通道（免费额度、Count≤5、QPS 5）。
- YOLO+CLIP 细节：YOLOv8n/s 定位可行；Chinese-CLIP ViT-B/16 作为特征 backbone 可行（我们已有 UForm3/Chinese-CLIP 经验）；但**不要用 CLIP 相似度直接判型号**，要用“同族参考 + 阈值 + 人工抽检”。

## 3. 对我们两个阶段的影响（量化视角）

| 机制 | 落点 | 预期收益 | 代价/风险 | 采纳 |
|---|---|---|---|---|
| 豆包 image 通道 | 【第一段】召回 | 可能降低死链、提升中文工程车覆盖；标题带码率未知 | 免费额度仅 ≈1 轮；Count≤5；QPS 5；依赖账号 | **A/B 后定** |
| 权威分（AuthInfoLevel） | 【第一段】排序 | 低；把“官网/行业媒体”提前 | 需要 web 模式 | **可试**（低成本） |
| LLM 型号冷启动 | 【第一段】查询种子 | 可能补到未想到的官方型号 | 幻觉/过时；成本 | **仅种子，不入池** |
| 官方命名优先级 | 【第一段】排序 | 中；带码候选更可能 confirmed | 需定义“官方命名”（用码/来源） | **采纳** |
| 视觉参考库 + k-NN | 【第二段】证据 | **最大**：把“标题无码”的 unknown/probable 升到 A 级 | 假阳性、基准污染、算力、许可 | **先校准再采纳** |
| 两级视觉（轻量+大模型复核） | 【第二段】 | 中；控制成本 | 大模型调用成本 | 视觉方案确定后再定 |
| 分级校验 | 【第二段】政策 | 中；把“热门/小众”区分开 | 需要 popularity 信号 | **采纳** |
| 反馈 Loop | 跨阶段 session | **大**：多轮修改不重跑全链 | 意图误判、状态复杂 | **采纳**（见 §4） |

**效率结论**：真正能提效的是“预索引通道 + 视觉初筛（少调大模型）”，不是“LLM 冷启动”。**质量结论**：真正能提质的是“视觉参考证据 + 分级校验”，但必须先证明假阳性率可接受。

## 4. Loop 设计：从用户输入到“正确的节点”

### 4.1 先厘清：反馈不是“重跑一次”，而是“打补丁 + 局部重跑”

我们的引擎是状态机（`BRIEF_READY → LIBRARY_SEARCH → FETCH → VERIFY → FILL → GAP_CHECK → …`）。
多轮交互的正确形态是：**把口语反馈转成 brief 的“补丁”（patch），定位到受影响的最小节点集合，只重跑这些节点**；交付**只增不减**。

### 4.2 反馈分类（专家的 6 类 + 我们补 2 类）

| # | 类型 | 例子 | 补丁 | 起始节点 |
|---|---|---|---|---|
| F1 | 视图/角度 | “要正脸，不要侧面” | `view_filter` | **FETCH**（改查询/筛选）或 **FILL**（重排） |
| F2 | 款型纠错 | “第 3 张不是沙漠版” | `asset.blacklist` + `model.verify_override` | **VERIFY** → **FILL** |
| F3 | 质量 | “要高清、不要水印” | `min_width/watermark` | **FETCH** 的过滤 / **FILL** |
| F4 | 数量扩充（同型号） | “这个型号还有更多图吗” | `target.quota+` | **FETCH**（同 target） |
| F5 | 品牌/车型扩充 | “再找几个陕汽的” | `plan.add_targets` | **EXTERNAL_DISCOVER/plan** |
| F6 | 排除约束 | “不要挂车/把北奔去掉” | `negative_terms` / `exclude_brand` | **plan**（查询负词）+ **FILL** |
| F7 | 部件细节 | “看前脸格栅” | `part_requirements` | **FETCH**（part 查询） |
| F8 | 范围/配额（新增） | “多来点邻近车型”“只要精确” | `scope.ratio` | **plan**（scope） |
| F9 | 交付/呈现（新增） | “再补 2 台”“按品牌分组” | `page_budget` / `presentation` | **FILL/交付** |

### 4.3 意图识别：结构化输出 + 规则校验 + 歧义兜底

LLM 输出（一次调用，小样本提示即可）：

```json
{
  "patches": [
    {"target": "view_filter", "op": "set", "value": {"views": ["front"]}, "confidence": 0.92},
    {"target": "plan.add_targets", "op": "add", "value": {"brands": ["陕汽"]}, "confidence": 0.8}
  ],
  "destructive": false,
  "clarify": null
}
```

规则校验（代码）：
- `target` 必须是白名单节点；`value` 必须过 schema；
- 与旧约束冲突 → 新覆盖旧，但写 `superseded_by`；
- `destructive=true`（删/替换已交付）或 `confidence<0.6` → **只问一个问题**再执行；
- 一条反馈最多产 3 个 patch；超出先拆。

### 4.4 状态与版本

- `Session`：`brief_versions[]`、`constraints{hard, soft}`、`delivered[]`、`blacklist[]`、`preferences{}`、`rounds[]`；
- 每次 patch 生成新 `brief vN`，只重跑受影响节点；未受影响节点复用上一轮产物（按内容哈希缓存）；
- 交付清单带 `round`、`added_by_feedback`，**永不删除**历史交付；
- 所有 patch 与重跑范围写入 `summary.config.session`，可回放。

### 4.5 多轮示例（专家例子的修正版）

用户：“第三张不对，不是沙漠版，而且我都要正脸图，再多来几张陕汽的”
1. **路由**：F2（黑名单 asset#3 + 降权该 model）→ VERIFY/FILL；F1（view=front）→ FETCH；F5（add brand 陕汽）→ plan；
2. **补丁**：`blacklist{asset:3}`、`views=[front]`、`add_targets{brand:陕汽}`；
3. **重跑**：只跑 陕汽 target 的 FETCH + 全量 FILL 重排；不重跑其他 target；
4. **交付**：新增 2 台陕汽正脸图，替换第 3 张，其余不动；版本 +1；
5. **记忆**：`preferences.views=[front]`、`preferences.brands+=陕汽`；下轮默认生效。

### 4.6 常见失败模式

- **意图误判**（“不要这个”到底删图还是删型号）→ 破坏性操作必须确认；
- **补丁冲突**（“要正脸”+“这张侧脸很好”）→ 以显式 patch 为准，软偏好降级为排序；
- **无限重跑** → 每轮 delta 预算上限（查询 ≤25%、抓取 ≤20%），超限提示；
- **记忆污染** → 偏好只在 session 内生效；跨 session 需显式确认。

## 5. 产品、护城河与垂直价值（批判性）

### 5.1 合理性

- 真实痛点成立：设计竞品调研要“找对型号、找全角度、能溯源、能出图”，通用搜索做不到；我们三轮数据也证明“型号确认”是核心难点（41.1% confirmed）。
- 用户画像清晰：工程机械/专用车 OEM 设计部门、工业设计咨询、行业媒体/研究。
- 单点价值可量化：一次调研 10 台车，人工 2–3 小时 → 工具 10 分钟 + 可复核。

### 5.2 真护城河 vs 伪护城河

| 专家列的 | 判断 |
|---|---|
| 数据结构化深度（部件/改款/演化） | **真**，但要持续人工+自动积累 |
| 工作流编排（找图-验真-分析-导出） | **真**，且是我们已有基础 |
| 准确率定制（视觉特征库） | **真但难**；需数据与校准，不是一次性工程 |
| 工程化/批量 | **半真**：能防抄，但不是壁垒 |
| 私有化部署 | **真**（企业付费点），但重 |

**被专家漏掉的、我认为更硬的护城河**：
1. **可核验的证据链**（每张图有出处、型号证据等级、可审计）——设计院/车企最需要的不是“更多图”，而是“敢用的图”；
2. **领域评估数据 + 反馈闭环**（哪些图被设计师采纳/否决，形成难复制的偏好数据）；
3. **与报告工作流的绑定**（不是搜图工具，而是“调研报告生产线”）。

### 5.3 垂直价值与商业模式

- **垂直价值高**：工程/专用车是“型号多、外观近似、公开资料散”的典型，通用模型在这里最弱；越垂直，视觉参考库越有价值。
- **商业模式**：B 端私有化/团队版（按席位/项目）> C 端订阅；个人设计师可做免费/低价入口。
- **风险**：图片版权与来源 ToS；平台 API 依赖（豆包/百度）；“准确率承诺”带来的责任；单人维护成本。
- **定位建议**：**“证据可核验的工程车辆设计调研工作台”**，而不是“AI 搜图”。搜图是入口，报告与证据是产品。

### 5.4 是否值得专门做这个工具？

**值得，但前提是**：把资源压在“参考库 + 证据链 + 报告工作流”，而不是“再做一个搜索”。如果只做检索，通用工具+API 就能覆盖，护城河不成立（专家这句是对的）。

## 6. 若要采纳，架构上怎么改（允许重来）

| 模块 | 现状 | 建议 | 是否重来 |
|---|---|---|---|
| 召回 | `imagesearch` 三通道（360/百度/必应）+ 下载 | 抽象成 `Channel` 接口，新增豆包/必应 provider；统一元数据（title/site/authority/width/watermark） | 局部重构 |
| 文本证据 | `identity.py` 码匹配 | 保留；增加“权威分/官方命名”排序特征 | 否 |
| 视觉证据 | 只有 `gate` 零样本 | 新增 `visual_evidence`：YOLO 裁车 → CLIP 特征 → 参考库 k-NN；输出 A1–A3，不覆盖 E1/E2 | 新增 |
| 参考库 | 无 | 新增 `reference_store`：按型号存 3–5 张高置信参考 + 特征；入池需文本高置信 + 人工抽检；增量需复核 | 新增 |
| Loop | engine 内 replan | 新增 `session` + `router`：patch → 最小节点重跑 → 增量交付 | 新增 |
| 交付 | 单次 manifest | 增量版本、role/tier 标注、可回滚 | 扩展 |
| 评估 | 交付/身份 | 新增：exact integrity、A 级准确率、多轮收益、成本 | 扩展 |

**不建议重来的**：状态机、身份匹配、门卫、证据库、报告链路——这些是已验证资产。
