## 1. 模块版图：三模块骨架 + 两个缺位【初步共识】

讨论确认的价值主链为"检索 → 分析整合 → 排版"，但按真实工作流补齐两块不属于主链、缺一不可的部分，版图定为五块：

| # | 模块 | 职责 | 与 PRD 的关系 |
|---|---|---|---|
| 0 | 素材资产库 | 实拍图/历史项目图/网络补充图统一入库：识别打标（车型/部位/视角）、裁图、授权标记 | FR-1.1 的底座，被检索/分析/排版跨模块复用 |
| 1 | 检索模块 | 联网检索（名录/参数/图片）+ 资产库/历史项目检索 | FR-1.2 |
| 2 | 分析整合模块 | 按统一 schema 产出结构化分析；缺口检测反向驱动检索补充 | FR-2 |
| 3 | 报告规划模块 | 页型规划、素材充分性评估、检查点设置、模块编排 | FR-4 |
| 4 | 排版模块 | 模板填充生成 PPT | FR-5 / FR-8 |

- 图片是本项目的一等公民，素材资产库的结构决定后续一切；
- 报告规划是编排大脑：没有它，主链只是一条不会思考的流水线。

## 2. 统一分析 schema：整个系统的公共合同【初步共识】

分析整合模块输出的结构化格式一次定义、四处共用：检索按它找缺口，分析按它填内容，排版按它渲染，知识库按它沉淀。这是全项目最承重的设计决策，应尽早投入。

维度建议（在讨论提出的两维度上补一维）：

| 维度 | 内容 | 对应行业写法（报告增强研讨稿 §2.2 四段式） |
|---|---|---|
| 结构信息 | 形态/构型/参数等客观事实 | 第 1 段（形态/图形变化） |
| 设计信息 | CMF、姿态、比例、特征线 | 第 2–3 段（材质工艺 / 姿态比例） |
| 设计意图 | 为什么这样设计、给用户什么价值 | 第 4 段（设计意图/用户价值） |

术语口径与附录 B 词表及研讨稿 §2.2 术语栈对齐；schema 中须含溯源字段（来源 URL / 素材 ID / 人工确认状态），支撑 NFR-6。

## 3. 检索模块交互范式：对话为壳、结构化对象为核【候选思路，待确认】

- 不做纯聊天窗口（长对话迷失、错误结论难回滚、修改无法精确定位——智能客服行业的成熟教训），也不做死板表单（立项需求模糊，表单填不了模糊）；
- 混合式分工：**对话负责**澄清、确认、纠偏；**结构化对象负责**承载确认结果——名录是一张可勾选表格、素材缺口是一块看板、报告大纲是一页大纲图，修改发生在对象上而非继续聊天；
- 工程路径：先做引导式问答（任务型对话 slot-filling：置信度高静默推进、低才追问），自由对话后置；MVP 先做"引导式问答 + 确认页"；
- 六个对话触点：① 立项确认设备类别与竞品范围；② 候选名录勾选增删 → **锁定为闭集**（即闭集匹配的建库动作）；③ 素材充分性评估结果确认；④ 网络检索结果逐条采纳（含授权合规确认）；⑤ 分析文案审校；⑥ 报告页型规划确认；
- 附加价值：每次确认与修改都是偏好数据，与 §4 的进化式沉淀衔接。

## 4. 知识沉淀路线：进化式沉淀，不做一次性 RAG 建库【初步共识】

背景：工程车辆内容大量重复（吊车/矿卡/沙漠牵引车等多为卡车模板的变体）。一次性建 RAG 库的四个顾虑——无现成语料、从零处理慢、一次性加工质量未知、存了也未必适配具体场景——均成立。

**结论：采用进化式路线（数据飞轮）**——每次项目按统一 schema 结构化沉淀，持续积累。论证要点：

1. **沉淀零边际成本**：分析模块本就必须输出结构化结果（为排版服务），项目产出天然就是知识库记录，知识库是副产品而非额外工程；
2. **质量锚定人工确认层**：入库的是经检查点确认过的结论，修改行为即沉淀，越用越准；
3. **存"确认过的事实与素材"，不存"现成答案"**：旧条目检索出来后作为参考材料，按当前主题/环境重新生成文案，不复制粘贴——场景适配（如沙漠工况）化解为检索过滤 + 重新生成，不靠存储解决；
4. **层级继承结构利用"变体"观察**：平台层（重卡基础构型，存共性）→ 变体层（矿卡/沙漠版，只存差异与覆盖项）；检索时先继承后叠加，与设计师"先看共性、再看差异"的对比思维同构；
5. **旧报告机会式入库**：新项目涉及某类目时顺手补录相关历史报告，不做集中批量处理。

技术形态：前期轻量——结构化元数据库 + 图片对象存储 + 按类目/工况/地域过滤的检索；实体关系复杂后再考虑知识图谱升级，不提前投入。

## 5. 成熟架构静态对照【调研输入，待联网核实】

| 本项目问题 | 成熟对应物 | 可借鉴思路 |
|---|---|---|
| 联网检索名录/参数/图片 | Perplexity、秘塔等 AI 搜索；Agent 联网检索 | 结果必带来源清单，人工逐条采纳 |
| 对话确认 | 任务型对话（slot-filling）+ 生成式 UI | 对话驱动，关键节点落成可点的确认卡 |
| 结构化分析输出 | 企业非结构化数据抽取（合同要素/简历解析） | schema 即合同，一次定义多处共用 |
| 图片识别、打标、授权 | DAM 数字资产管理（Adobe AEM/Bynder）+ 以图搜图 | 授权字段进 schema，图片一等公民 |
| 闭集匹配（名录→照片对号） | 安防/电商 1:N 比对（先建底库后对号） | 置信度低转人工，不硬猜 |
| 知识沉淀 | Glean（连接既有内容而非重建语料）、数据飞轮 | 工作过程即知识生产 |
| 排版生成 | Gamma、WPS AI 等 AI PPT | 内容结构 → 模板槽位填充式生成 |

与智能客服的本质区别：客服是"问答"（用户要答案），本项目是"生产"（用户要交付物）；更贴近的同类是企业知识工作自动化（合同审查、尽调报告、AI PPT）这类"带人工检查点的文档生产线"。

产品启发五条：
1. Perplexity 的引用交互（结论悬停可见来源）→ NFR-6 溯源的现成交互范式；
2. Gamma 的"大纲先行、逐页生成、页级编辑" → 报告规划模块的交互范式；
3. Glean 的"连接而非重建" → 印证旧报告机会式入库，不造语料工程；
4. DAM 的权利元数据 → 图片授权状态（甲方授权/自摄/网络待确认）为资产库必填字段，NFR-7 合规卖点落到数据结构；
5. 底库-对号范式 → 识别口径从开放集准确率改为闭集匹配准确率，更可行也更可承诺。

## 7. 对标检索发现（GitHub 优先，2026-10-07 执行）

执行方式：GitHub API 搜索（按星标排序，6 组关键词）+ 重点项目 README 深读（4 选 2 成功）。全程单请求 30 秒超时、失败不重试循环。星数为当日快照。

### 7.1 轮 1：AI PPT / 排版生成

| 项目 | 星数 | 状态 | 要点 |
|---|---|---|---|
| Anionex/banana-slides | ~15.7k | 活跃 | 一站式 AI PPT：一句话/大纲/页面描述生成、上传模板图片控制版式、素材智能解析、**口头修改指定区域**（对话式编辑）、导出可编辑 PPTX、项目历史与可复现工作流 |
| presenton/presenton | ~11.0k | 活跃 | 开源 AI 演示生成器 + API（对标 Gamma/Canva），可作排版模块集成候选 |
| allweonedev/presentation-ai | ~3.0k | 更新中 | Gamma 替代品，主题 + AI 内容生成 |
| Akxan/ppt-agent-skill | ~0.2k | 更新中 | 26 风格 / 18 图表的 Skill 形态生成器，模板风格库组织方式可参考 |

**对标结论**（对应本稿 §3、PRD FR-5/FR-8）：
- banana-slides 印证"对话为壳、结构化对象为核"：输入侧吸收模糊（一句话/大纲/模板图），编辑侧走对象化修改（指定区域口头修改），产物始终是可编辑 PPTX——与本产品交互路线一致；
- 注意其生成技术路线（图像模型直出）与我们所需的"结构化槽位渲染可编辑 PPTX"不同，借鉴交互范式而非渲染技术；
- "上传任意模板图片控制版式"提示模板资产轻量形态：不必先建完整母版系统，模板参考图 + 结构化槽位即可起步（FR-8 MVP 形态参考）。

**对标结论**（对应本稿 §2/§4）：
- FastGPT 验证进化式沉淀的两个关键机制已在成熟产品落地：① chunk 级人工修改删除 = 我们的"确认过的事实入库、修改即沉淀"；② 引用可点、可纠错 = NFR-6 溯源交互的现成形态；
- 我们的知识单元（车型-部位-变体继承）比文档 chunk 更结构化，GraphRAG/KAG/graphify 的实体图谱路线为后期升级方向提供实证，当前"轻量起步"决策不变；
- FastGPT 的可视化 Flow 编排是报告规划模块编排形态的候选（检查点 = 人工节点），但 MVP 是否需要可视化编排存疑，倾向代码态编排 + 结构化确认页（留待架构方案）。
