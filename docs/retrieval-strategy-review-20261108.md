## 2. 先纠正一个框架：这不是"答案引擎"

专家开篇把问题放进"搜索式 AI（Perplexity 类）"的框架里：输入问题 → 获取、清洗、排序 → 输出带引用的答案。

**我们的产品不是这个形态。** 我们的输出是**一份 20 页的设计参考报告**：12 个整车页 + 部件专项页，每页要 1–2 张主图 + 3–4 个部件裁图 + 结构化分析。用户要的不是"一句话答案"，而是**能排进版面的、可归因的视觉证据**。

这个差别决定了三件事：

1. **"检索质量 80% 由排序决定"不适用于我们**。我们的瓶颈在"有没有合格主图、图是不是这台车"，不在"几百个候选怎么排"。项目实测也印证：`l3gate` 把文本精确率从 40.4% 拉到 93.1% 后，真正的缺口变成了召回薄（V/P 3.2%/12.9%）和身份不可验证。
2. **"证据"的单位不是段落，是"图 + 部件 + 型号 + 可用性"**。所以专家说的"三证核验"比"重排"更贴近我们。
3. **页数预算是硬约束**。专家全程没有提页数；而我们的清单不是"越全越好"，是"12 个页槽能不能填满"。

**结论**：借用专家的**问题清单**，不借用他的**答案引擎技术栈**。

## 3. 专家意见逐条评估

### 3.1 部件-环境相关性分类器 —— ✅ 采纳，但落成 L1.5 的一个字段

**专家主张**：检索前先对"车辆类型 × 部件"逐个打三值标签（强相关/弱相关/不相关），强相关才找沙漠工况实拍，不相关就忽略"沙漠"这个修饰词；做成可配置矩阵 + LLM 零样本推断 + 人工复核沉淀。

**项目现状**：这是**对的，而且我们已经有半个骨架**。`roster-expansion-design.md` 的四轴（`exact / environment / platform / cross_vehicle`）已经在做"该不该扩展、往哪扩"；部件→视角映射（`part_views.json`）也设计了。**但缺的是"每个部件对环境是否敏感"这个判断**——现在四轴是全局的，不是按部件生成的。

**判断**：采纳。它不替代四轴，而是四轴的**输入**：

```
部件 × 环境 → env_relevance ∈ {strong, weak, none}
  strong → 默认开 environment 轴，且要求"该部件在工况车上的实拍"
  weak   → environment 与 platform 都收，按证据质量排序
  none   → 关掉 environment 轴，在 platform/cross_vehicle 里找"设计质量"
```

**落地**：不要新建"分类器模块"，在 L1.5 的 target 里加字段：

```json
{"part": "前脸", "env_relevance": "none",
 "axis_plan": ["platform"], "accept": "已知型号 + 前 45° 实拍 + 可裁前脸"}
```

初值写进 `data/part_axes.json`（12 个常见部件 × 4 类目），LLM 只对新部件做零样本推断，人工复核后回写。这与 D3"知识放数据、判断放模型"一致。

**注意**：专家把"前脸"直接判成"不相关"，这个例子对沙漠牵引车成立，但不能推广成"前脸永远不相关"——矿山/寒区的前脸可能有进气防护、灯罩、防撞结构。所以 `env_relevance` 必须是**类目 × 部件 × 工况**三元组，不是部件常量。

---

### 3.2 "推荐名单 → 找图"是线性的 —— ⚠️ 设计已反转，实现与交互仍线性

**专家主张**：不要把"推荐车型名单"和"获取图片"当线性步骤；应先定义"对这个部件什么才算有效视觉证据"，再倒推要找什么车、去哪找。

**项目现状**：**设计层已经这么做了**。`roster-expansion-design.md` §3.3 的"合格主图"判据（单台/分辨率/视角/可裁）和 §6 的"惰性放闸"（触发条件是图片不够，不是文本不够）就是"证据先行"。但：

- **代码 0**：M0–M4 一步都没实施；
- **交互仍是线性的**：S1 让用户确认清单 → 进 S2 找图。如果图不够，清单要不要回头改？现在没有定义；
- **确认包是硬门**：一旦确认，清单就固化了。

**判断**：专家在"实现层"的批评成立。建议把 S1 的确认从"定稿"改成"**暂定清单（provisional）**"：确认的是"检索方向与页槽数"，不是"这 12 台车必须存在"；检索后按主图/可裁结果自动降级、备选转正，并落账。UI 暂停期正好先把这个规则写清楚，等恢复时再改交互。

**同时要指出专家漏掉的一点**：名单的边界不是"准"，是"页槽填得满"。我们已经有超量推荐（推荐 N + 备选 2–3）、备选不占槽、转正才占槽的规则；专家没有页数概念，不能照搬"全量高质量卡车"的开放检索。

### 3.3 先文后图 / 先图后文 —— ⚠️ 部分采纳，预算约束下不能全量

**专家主张**：强/弱相关部件走"先文后图"（文本建立语义锚点，防止视觉噪声带偏）；不相关部件走"先图后文"（视觉检索 + 反向确认型号）。

**项目现状**：两条通道都有，但**没有串联**：

- 文本：`textrun` → SERP → 段落 → `l3gate`，产出薄（V/P 3.2%/12.9%）；
- 图片：`imagesearch` → `_relevant` 标题护栏 → `gate` 门卫 → 视角；
- 现状是"文本检索"和"图片检索"各自独立，靠人衔接。

**判断**：方向对，但**不能每个 target 都先文后图**。项目已经定了"文本只跑推荐集，备选不跑"（`roster-expansion-design.md` §7），因为文本单次成本高、A 档产出低。正确做法是**分级**：

| 情形 | 通道 | 理由 |
|---|---|---|
| `strong` 部件 + 证据库无记录 | 先文后图 | 需要"沙漠工况下这个部件有哪些已知变体"作为锚点 |
| `weak` 部件 | 图为主，文本只查已有证据库/缓存 | 不值得为每个 target 跑一次完整文本检索 |
| `none` 部件 | 先图后文（型号/元数据过滤 + 视觉确认） | 设计自由度大，视觉检索更直接 |
| 证据库已有 | 直接召回，不检索 | 这是证据库的核心价值 |

**专家警告的"视觉泛化噪声"是对的**：T14 的四组构型混杂（STC800C6 / XCT8L4 / QY16KC / QY25K5C）和 T13 的 J6G 错配就是实证。所以"先图后文"必须配元数据过滤和身份核验，不能只靠视觉相似度。

### 3.4 三证核验 —— ✅ 采纳；两证有零件，第三证空白

**专家主张**：检索后不要只判"图文相关"，要做三证：① 型号-图片归属；② 部件-图片可见性；③ 改装/原厂状态；输出带置信度和缺陷标签的证据记录，而不是二值。

**项目现状**：

| 证 | 项目已有 | 缺口 |
|---|---|---|
| ① 型号-归属 | 标题含型号代码、构型词一致、品牌命中、`gate` 类别门卫、人工复核；`evidence-index` 的 E1/E2/E3 | `region_match` 未实装；CLIP 零样本判不了身份（T12/T14 已证）；反向搜图无 |
| ② 部件-可见性 | 分析 schema 的 `visible: full/partial/not_visible` + bbox；`probe` 视角；`gate.check_exterior` | 检索阶段没有"可裁"粗判（`part_views.json` 未建）；可见性目前是"分析后"标签，不是"检索时"标签 |
| ③ 改装/原厂 | **空白** | 高改装部件（防护栏/保险杠）恰恰是重点；机器判不了，人工标注成本高 |

**判断**：三证都该做，但优先级不同：

- ① 是**当前最硬的缺口**（诊断文档 §2 已排序）→ 先做 `region_match` 或候选聚类，别指望 CLIP；
- ② 是**最便宜的增量**（视角 + 分辨率 + 分析 `visible` 回填）→ 先建 `part_views.json` 和 `cropfeasible()`；
- ③ 是**最贵且最不确定**的 → 先人工抽标 20 张校准，再决定自动化；落地为 `origin_status ∈ {oem, modified, unknown}` + 降权，不做取证级。

**输出形态**：专家说"带置信度和缺陷标签"，这与我们已有的 evidence schema 一致。建议扩一条 `image_evidence` 记录（见 3.6），不要另起一套。

### 3.4a 来源分层（JSON-LD → 经销商 → 专利）—— ⚠️ 方向对，"JSON-LD 优先"不现实

**专家主张**：来源分三层——优先有 JSON-LD 结构化标记的页面（如 Volvo CE），次级是需要渲染但结构规整的经销商/垂直站，兜底是外观设计专利库。

**项目现状**：`data/source_registry.json` 已有域名信任分级，`domainbench.py` 能按"同查询跨站对照"给域名升降级（曾把 yoojia 提为 high）。但**没有 JSON-LD/结构化数据解析**，也没有"经销商层"的显式分层。

**判断**：

- **方向对**：来源分层与 `source_registry` + domainbench 是同一件事，应该继续用数据驱动，不写死域名。
- **"JSON-LD 优先"不现实**：工程机械中文官网的产品参数大量是图片、菜单靠脚本拼接（专家自己也引用了这条行业观察）；能稳定提供 JSON-LD 的主要是 Volvo CE 这类国际品牌，覆盖不了长尾类目。把它当"优先层"会让大多数查询直接掉到次级层，等于没分层。
- **真正的中间层是经销商/垂直站**（360che、21-sun、yoojia 等），这也是 domainbench 已经在排序的对象。
- **专利不是"兜底"**，是另一种证据形态（线稿、无 CMF），应作为独立通道（见 3.7），不要和"官网图不够就用专利"混在一起——否则会拿线稿去补 CMF 的缺口。

**落地**：在 `webchannel` 加一个**可选**的 `structured_data` 探针（有则用，无则跳过），不改变主排序；来源优先级仍由 `source_registry` + domainbench 决定。

### 3.5 分析模块反向裁判 —— ✅ 采纳，但必须抽样 + 先校准

**专家主张**：检索的验收标准不是"找到足够多图"，而是"图能让分析模块产出高置信度结论"；把分析模块当证据质量裁判，形成以分析可用性为终点的闭环。

**项目现状**：`analysis.py` 有 schema 校验（`validate_analysis`）、可见性、三词、构型名检查；`analyze_batch.py` 能批量跑。但**没有金标评测**——"分析模块已经有效"目前是产品负责人的主观判断，不是数字。

**判断**：方向完全正确，但有两个必须提前处理的问题：

1. **循环论证**：分析模块既是"被验证对象"，又是"裁判"。如果它的输出本身有偏差，裁判会把偏差固化。**必须先用 50 张人工金标校准**，再让它当裁判。
2. **成本/延迟**：专家自己也提示"可能要做抽样裁判"。我们的 VLM 是后置决策（D7），如果每张图都调用，检索会被分析卡住。建议：

```
evidence_score = schema 完整度(0.4) + visible(0.3) + 关键字段非空(0.2) + 人工复核(0.1)
只对"边界图"（分辨率低/角度偏/身份存疑）抽样 10–20% 做裁判，其余用规则分
```

**验收**：`evidence_score` 与人工"这张图能不能用"的判断一致率 ≥ 80%，才允许进入自动闭环。

### 3.6 证据库 —— ✅ 最高杠杆，采纳为主线

**专家主张**：不要每次从全网重检；把三证核验通过的图文对沉淀成"部件-环境证据库"，优先召回，覆盖不足再外检；这是复利最高的投入。

**项目现状**：我们自己的 A/B 已经得出同一结论——**证据基础设施 > skill 纪律**：skill v0.2 的填充率 85.4%，但真正验证到车型的只有 9.4%；而 E3 证据索引把两臂都拉到 11/12。`evidence-index-20261031.json` 有 24 车型 / 654 篇 / 85 条 E3，**但只有文本，没有图片-部件证据**。

**判断**：这是本轮最该做的一件事，优先级高于任何框架迁移。建议建一张表（SQLite 即可）：

```sql
image_evidence(
  id, asset_id, vehicle_id, model, part, view,
  resolution, identity_status,       -- confirmed / probable / unknown
  origin_status,                     -- oem / modified / unknown
  visibility,                        -- full / partial / not_visible
  evidence_grade,                    -- E1/E2/E3
  source_url, run_id, verified_by, verified_at,
  evidence_score
)
```

检索流程改为：**先查库 → 命中即用 → 不足才外检 → 核验后回写**。这样"越用越快、越用越准"，也直接降低 360 单通道的压力。

**先做多大规模**：不用等全量。现有 70 张过门卫的图 + 分析结果，人工核验 50 条录入，先跑通"查库优先"的路径。

---

### 3.7 外观专利库 —— ⚠️ 有条件采纳：只做形态，不做 CMF

**专家主张**：外观设计专利是"去语境化、聚焦造型、带型号/申请人元数据"的高质量视觉证据，对"前脸造型参考"可能比官网宣传图更干净。

**项目现状**：完全没有这条通道。

**判断**：想法有价值，但专家低估了**形态不匹配**：

- 外观专利多为**线稿/渲染图**，没有材质、颜色、表面处理 → 分析 schema 的 `cmf.material_class` / `finish` 无法产出，只能支撑 `form / proportion / character_lines / gesture`；
- 专利图常是**六视图拼版**，需要切分；"实施例"不一定是量产形态；
- CNIPA 检索有验证码、无公开 API，抓取合规性要核实；Google Patents / 专利汇可先做小样本。

**落地**：作为**形态参考的补充通道**，不替代实拍主图；先做 **10 件**可行性测试——如果分析输出大量 `null`（CMF 字段），就只做"人工看图参考"，不进自动分析。**不要现在排期**，等 P0 做完再评估。

---

### 3.8 Firecrawl / Tavily / SearXNG —— ❌ 不整体采纳；✅ 付费 API 做对照实验

**专家主张**：把"网页获取"外包给 Firecrawl/Tavily，或用 SearXNG 聚合，换稳定性。

**项目现状**：诊断文档已经做过归因（§3）：**真浏览器（Crawl4AI/Playwright）渲染百度仍被拦**，瓶颈是出口 IP + 请求模式 + 无登录态，不是"浏览器不够像人"。Firecrawl 的反爬主要解决 Cloudflare/JS 渲染，不解决百度封 IP；SearXNG 底层还是 Bing/Google 等，中文工程机械长尾覆盖未必好。

**判断**：

- **不采纳**"换获取层"作为架构动作——项目已经有 `channels.py`/`webchannel.py` 和严格的通道状态（`ok/empty/blocked`），换一层不解决身份核验；
- **已满足**：他说的"把被阻止页面和空页面当一等公民"我们已经做到——`imagesearch` 回传 `ok/empty/blocked:X`，`runner` 记录降级链与重试；这条不用改；
- **采纳**诊断文档 P2 的"官方/付费检索 API 评估"：用同一批 20 条查询，对照 Tavily / Serper / Bing 的中文工程机械召回率、单条成本、延迟。这是**一周的对照实验**，不是架构迁移；
- SearXNG 可作为免费备选，但不必现在投入。

---

### 3.9 LangGraph / Dify / n8n —— ❌ 不采纳为平台，✅ 借思想

**专家主张**：主流程 Workflow、两个节点用 Agent；LangGraph 比 LangChain 合适；前期用 Dify/n8n 验证，后期迁 LangGraph；私有化部署。

**项目现状**：我们**已经有一个可跑、可回放、可审计的确定性编排**：

- `runner.py`：有限重试、通道降级链、断点续跑（状态 JSON 原子写）；
- `strategy.py`：replan/stop/ask_user；
- `runlog.py` + `data-test/runs/`：每次运行有账本；
- 离线回放 6,806 段，可复现。

这些是**产品资产**，不是技术债。

**判断**：

- LangGraph 的核心价值（条件边、检查点、有界循环）我们已经用手写代码实现了；引入它的收益主要是"可视化/生态"，成本是**重写 + 新依赖 + 复现性风险**。单人产品阶段不划算。
- Dify/n8n 的"可视化编排"对一个已经用 CLI 跑通全链路的项目是**额外维护面**，而且会把 schema/测试/账本打散到 JSON DSL 里。
- **采纳它的三个思想**，不换骨架：
  1. **任务单（task order）作为契约**：检索前输出的是"每个部件一条任务单"（目标、相关性、通道、来源优先级、验收条件），不是"车型名单"；
  2. **有界纠错**：裁判可以退回补充检索，但 `max_retry` 写死，超限转人工；
  3. **检查点**：已有 `runner` 的断点续跑，继续保持。
- 如果未来要做"多步动态检索"，可以在 `runner` 之上加一个薄 `orchestrator` 接口，LangGraph 作为**可选实现**，不绑定。

**一句话**：专家在"框架选型"上给的是 2026 年通用答案，我们的项目已经用更小的代价拿到了同样的能力；现在换框架是负收益。

---

### 3.10 Milvus / Qdrant —— ❌ 暂不采纳

**专家主张**：图文混合检索用 Milvus，轻量用 Qdrant；图片检索做"视觉召回 + 元数据过滤 + 多模态重排"。

**项目现状**：63 台 / 629 张图 / 85 条证据；SQLite + dHash + 全文检索足够。核心流程是**外网检索 + 人工确认**，不是固定语料 RAG。

**判断**：向量库在 **10^4–10^5 张图**或需要"跨模态语义召回"时才值得。现在引入会增加部署/运维/一致性成本，收益接近于零。**先做证据库（SQLite 表），等数据量到了再换存储**——接口留好即可。

---

### 3.11 "检索质量 80% 由排序决定" —— ❌ 对本项目不成立

这条是通用搜索/RAG 的经验判断，但我们的诊断（`retrieval-diagnosis-20261103.md` §2）已经把短板排序为：

1. 通道单点 + 无换路能力；
2. 相关性判断只在标题文本上；
3. **门卫只判"是不是工程车"，不判"是不是这台车"**；
4. 已有能力盘点（dHash/CLIP/视角/类别门卫）；
5. 降级链实际等价于单通道 + 一次重试。

**排序不是前三。** 把预算投到 reranker 会错配。投到**身份校验 + 证据库 + 通道健康度**才是杠杆。

---

### 3.12 AI slop / 内容清洗 —— ⚠️ 边际收益低，不优先

**专家主张**：AI 生成的低质内容正在污染搜索，需要结构性/重复性/空洞性检测（Pangram、ClearWater）。

**项目现状**：`l3gate` 已经在做对象锚定、主题排除、具体性要求，假阳性 6.9%；工程机械领域的主要污染是**营销/参数页/无关图**，不是 AI slop。

**判断**：不新增专门检测器。可以把"模板化营销文案"作为 `l3gate` 的一个弱特征，但不值得单独立项。

## 4. 专家没覆盖、但项目必须自己回答的

1. **页槽预算**：报告 20 页、整车页 10–14、一车一页、3–4 个部件裁图。清单不是"推荐得越准越好"，是"12 个槽填满 + 2 个专项页"。
2. **超量推荐与备选转正**：推荐 N + 备选 2–3；备选不占槽，转正才占槽；主图判废/人审驳回时按 priority 顶上，并落账。
3. **证据分级与"方向可占槽、型号不可"**：E1/E2/E3 + provisional 纪律——这是 A/B 打出来的，不是拍脑袋。
4. **文本不是门槛的实证**：T18-roster 只有 8/39 车型有 V/P 素材；文本检索的价值是定调/语汇，不是页槽成立条件。专家几处建议（先文后图、文本锚点）如果不加预算约束，会把成本拉回去。
5. **可复现/账本**：每次运行有 `run_id`、events、summary；这是产品信任的基础。任何"更灵活的 Agent"方案都不能牺牲它。
6. **人工确认是产品的一部分**：S1/S2 的确认不是过渡态，是"设计师选图"的核心交互。专家默认全自动，不符合我们的场景。

## 5. 主体功能成熟度与瓶颈排序

**成熟度（从高到低）**：L6 评估 > L3 闸门 > L4 控制 > L1 计划 > L5 分析（代码在、未验收）> L2 检索（可跑、产出薄）> 前端静态 > **L1.5 清单（0 代码）** > 证据库（0）> 部署（0）。

**瓶颈排序（按对"报告能不能交付"的影响）**：

| 序 | 瓶颈 | 证据 | 影响 |
|---|---|---|---|
| 1 | **清单不存在** | L1.5 设计 v0.2，M0–M4 未开工；`part_axes.json`/`part_views.json` 缺 | 用户输入"沙漠牵引车+5 部件"后，没有可确认的清单，S1 只能靠人 |
| 2 | **图片证据不足 + 身份不可验证** | 360 单通道；T14 四组构型混杂；J6G 错配；105→70 | 页槽填不满；填了也可能是错图 |
| 3 | **证据不可复用** | 文本索引 85 条，图片证据库 0 | 每次重检，成本高、质量不累积 |
| 4 | **分析无金标** | 代码在，无评测数字 | 不能当裁判，也不能证明"有效" |
| 5 | **前端未接** | 静态 v3.3 | 演示可以，产品不可用 |

**结论**：先做 1 + 3（清单 + 证据库），再做 2（身份校验），最后 4/5。**不要先换框架。**
