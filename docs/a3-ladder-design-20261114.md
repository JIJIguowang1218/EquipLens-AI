# A3 条件档设计：第几段、品牌怎么识别、值不值得（2026-11-14）

## 1. 先对齐“第几段”

| 段 | 代码 | 查询 | 引擎 | A3 是否服务这一段 |
|---|---|---|---|---|
| 第一段：出车型清单 | `scripts/plan_candidates.py` → `planning.build_query_plan` | 8 条中文查询（base/model/env/en/unit×2/topup×2） | DeepSeek Search（文本网页） | **否** |
| 第二段：抓图 | `retrieval_engine/web.py::live_fetch` → `query_variants` | 车型名派生的窄查询 + 全名 + 别名 | 图片搜索（360/Baidu/Bing） | **是** |

- 第一段的 `q-en` 并不是英文，而是“中文 + truck brands”提示（`沙漠牵引车 6×6 牵引车 truck brands`）；
- 本轮 A3 探针比较的是**第二段**：`normalize_query` vs `拉丁词+构型+truck` vs `型号码+构型+truck`。

## 2. 品牌识别现在到底准不准

用 `plan.json` 的 `brand` 字段（LLM 抽取，100% 有值）作伪金标：

| 指标 | 数值 | 说明 |
|---|---:|---|
| 车型有 brand 字段 | 100% | LLM 总会给一个 |
| `_brand_group` 能识别 | **33%**（650/1998） | 别名表 + 开头词兜底 |
| 与 brand 字段一致 | **43%**（280/650） | 大量是“品牌 vs 车系”混淆 |
| 不一致的例子 | — | `TX…` brand=中国重汽豪沃 → 识别成 `tx`；`Zetros…` brand=奔驰 → 识别成 `zetros`；`HF 8066` brand=MOL → 识别成 `hf` |

车型命名构成（1998 个候选）：

| 组成 | 占比 |
|---|---:|
| 含拉丁字母 | 74% |
| 纯中文（无拉丁） | 21% |
| 含型号码 | 45% |
| 含“非号码拉丁词”（可能是品牌/车系） | **44%** |
| 只有型号码、没有拉丁词 | 31% |
| brand 字段里有拉丁词 | **38%**（如 `三一（SANY）`、`雷诺（Renault Trucks）`） |

**结论**：`_brand_group` 不能当“品牌识别器”，它更像“第一个身份 token”，会混淆品牌与车系；
`plan.brand` 有值但有错（例：`OTTC` 的 brand 写成 `CLW`，与车型名不符）。
因此**不能直接用 brand 字段拼英文查询**。

## 3. 品牌识别的替代规则（可解释、不用表）

按证据强度排序，只用“能自证”的 token：

1. **车名里的非号码拉丁词**（`Zetros`/`HOWO`/`OTTC`/`KAMAZ`）→ 强证据，直接可用；
2. 车名里的型号码 → 强证据（作为查询主体）；
3. brand 字段里的拉丁词 → **只有**当它同时出现在车名或至少 1 条来源标题里时才算；
4. 其它情况 → 不做英文档（宁可不试，不制造噪声）。

按这个规则，10 个样本里 `OTTC`/`Zetros` 不会被误换成 `CLW`/`Mercedes-Benz`。

## 4. 条件档怎么设置才有效（第二段）

触发条件（全部满足）：

- 前三档（`normalize_query` / 全名 / 中文别名）**命中 0**；
- 存在“强证据拉丁 token”（规则 1 或 2）；
- 该 token 不是残缺前缀（如 `TAZ`、`PTUM` 这类被正则截断的片段）。

查询构造：

```
[拉丁 token] [型号码?] [构型?] [truck?]
```

- `truck` 只在车名含 `牵引/卡/货/越野/运输` 时加；叉车/压路机/正面吊不加（避免 `KLA truck` 那种噪声）；
- 不加中文品牌（中文品牌已在原查询里）；
- 档位记为 `query_tier="english"`（不是回退档，不进 degraded-only 限制）。

小样本验证（10 个 brand 含拉丁的车型，只搜不下载）：

| 档位 | 相关命中（>0） |
|---|---:|
| current | 3/10 |
| brand+code+构型 | **5/10** |

提升来自 `H6066`(MOL)、`Renault TRM700`、`Shacman 6x6`、`KAMAZ K-65959`；
变差的来自 brand 字段本身有错（`OTTC→CLW`、`Zetros→Mercedes-Benz`）——按 §3 规则会被过滤。

## 5. 第一段要不要加“翻译版本”的宽查询

**暂不建议**，理由按影响排序：

1. 第一段当前瓶颈是**抽取召回**（60–126 条结果只抽 30–40%），不是语言；
2. 翻译需要 LLM 或词表：LLM 翻译引入每次不同的英文措辞（破坏可复现），词表又违反“不要表”；
3. 英文结果页多是 OEM/出口站，标题/正文语言混杂，抽取与出处校验要额外适配；
4. 返回的英文车型名会进入第二段，若没有中文/拉丁对应关系，核验的标题 token 更对不上，`unknown` 比例会升。

如果将来一定要试，做法应是：**同一份 brief、同样 8 条查询，把其中 2 条换成英文**（不是额外加 2 条），
并同时测“候选数”和“候选可核验率”，不能只看数量。

## 6. 能用现有系统吗

- **第二段条件档**：可以。`query_variants` 加一档即可；`WebWorld.plan` 里已有 brand 字段，
  不需要改 schema；只需给 `Asset.query_tier` 增加 `english` 取值。
- **第一段翻译版**：不行。需要新增查询生成逻辑（LLM 或词表）与抽取适配，属于另一个机制。

## 7. 品牌 vs 车系：需不需要“模型识别”或“单独联网核对”

**先问影响面**：品牌/车系混淆只影响三处——中文别名生成、英文条件档、可读性；
**不影响搜索与核验**，因为那两处用的是 token 字符串，不是“这个词是不是品牌”的语义。

历史数据（按车名构成分组）：

| 车名构成 | target 数 | 0 命中率 | 有图率 |
|---|---:|---:|---:|
| 纯中文（无码、无拉丁） | 404 | **19.1%** | 55.2% |
| 只有型号码 | 405 | 1.0% | 84.0% |
| 含拉丁词 | 378 | 6.6% | 72.0% |
| 拉丁 + 型号码 | 369 | 2.4% | 80.8% |

同时：历史命中里最终胜出的查询档位是 `model` 63%、`exact` 33%、**`alias` 6%**。
也就是说，品牌知识唯一直接服务的 `alias` 档，胜出占比只有 6%。

**结论**：品牌/车系识别**不是当前瓶颈**；最痛的群体是“纯中文描述名”（19.1% 0 命中），
它们缺的是**可检索的标识**（码/车系），不是“这个品牌叫什么英文”。

### 三个选项对比

| 方案 | 成本 | 风险 | 能解决什么 |
|---|---|---|---|
| A. 加 LLM“认车型”调用（每候选） | 中（每候选一次 LLM） | 幻觉、不可复现、样本外车型更差 | 补 brand/英文名——但服务的是已经较好的 latin 组 |
| B. 单独联网核对（每候选 1 次 text search + 抽取，缓存） | 中（~¥0.005/候选，20 候选/brief ≈ ¥0.1） | 引入新 stage、抽取噪声、缓存与回放成本 | 同上；但比 A 可追溯（有出处） |
| C. **抽取阶段顺带输出 `search_key`**（品牌/车系/码，基于已读结果） | **≈0**（同一次 LLM 调用） | 依赖抽取质量；可用“码在车名里”校验 | 给纯中文名补可检索标识，不需要新查询 |

### 建议

1. **不做 A（模型凭记忆认车型）**：不可复现、容易幻觉，且收益落在非瓶颈群体；
2. **暂不做 B（单独联网核对）**：除非先证明 `alias` 档能显著提升；建议先做 20 个“纯中文 + 0 命中”样本的 spike；
3. **优先做 C**：在 `extract` 的 JSON 里增加 `search_key`（品牌/车系/码 + 构型），
   由抽取模型基于**已读到的来源文本**给出；plan 落盘时可复核（码必须在车名/来源里出现）。
   这不是“让模型认识车型”，而是“让模型把已读到的信息整理成可检索键”。


## 8. 结论

- A3 属于**第二段**；无条件英文档会伤召回，只能做条件档；
- 条件档的关键是“车名里有证据的拉丁 token”，不是“判断它是不是品牌”；
- 品牌 vs 车系混淆对搜索/核验**无影响**，只影响别名与可读性（alias 胜出仅 6%）；
- 值得先做的是 C（抽取时顺带输出 `search_key`，≈0 成本），而不是加识别模型或联网核对。
