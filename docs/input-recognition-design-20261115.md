# S0 用户输入识别与任务定义：评估与设计（2026-11-15）

> 对应台账：[`docs/external/doubao-consult-decisions.md`](external/doubao-consult-decisions.md) §1（S0-01…S0-06）。
> 2026-11-15 已拍板：S0-02/03/04/05 采纳（形态见 §6），S0-06 归档 → S3-05。
> 结论是**建议**；最终采纳/改进/不采纳由产品负责人拍板后写回台账。

## 0. 结论先行

1. **输入不能只当“车类型 + 数量”**。真实输入里混着 8 类信息：类目/工况、数量、品牌偏好（含外国品牌占比/指定品牌/排除品牌）、指定车型、用户提供的带型号图片、视角与质量、邻近范围、交付形态。必须落成 **TaskSpec**（任务单），再做规划和检索。
2. **解析不是“一句话丢给 LLM”**：LLM 负责语义拆解，代码负责**校验、缺省、冲突与澄清**；解析结果每个字段带 `source/confidence`，可审计。
3. **专家“LLM 领域知识冷启动”只适合做查询种子，不适合直接当候选池**。V6 实测：`deepseek-flash` 提出 65 个型号，**86.2% 能被搜索证实**，但只有 **7.7%** 与我们三轮真实检索池重合——说明它补的是我们“想不到去搜”的型号（尤其公告型号），而不是“已知型号的重复”。
4. **DeepSeek flash 够做种子生成，不够做权威池**：专业类目明显衰减（泡沫消防车 2/6、扫路车 4/6 可证实）；更大的模型可以提升，但仍必须过检索证据，成本不划算（见 §4.4）。
5. **冷启动 + 动态补全**：动态补全我们已有（SERP 抽取 + 合并 + topup），专家这条是“已实现”；冷启动作为**前置种子层**是增量，但要限量、可审计、失败不阻塞。

## 1. 用户输入的真实形态

| 类型 | 例子 | 影响 |
|---|---|---|
| 类目/工况 | “沙漠牵引车”“油田 6×6” | `class`、`environment`、`configuration` |
| 数量/交付 | “10 台”“8 主 2 备” | `page_budget.slots/backup_slots` |
| 品牌偏好 | “要覆盖陕汽、重汽”“外国品牌占 1/3”“不要北奔” | 查询覆盖、排序、排除、配额 |
| 指定车型 | “必须包含 H6066 6×6”“分析 Zetros 4051” | `pins`、目标锁定 |
| 用户给图 | 截图/照片，带型号字样或文件名 | 不检索；判 A/B/C 后作**额外交付**（source=user），并与抓取图一起进分析 |
| 视角/质量 | “要正脸”“不要水印”“高清” | 查询后缀、门卫过滤、排序 |
| 邻近范围 | “再配两台普通牵引车参考” | `scope`（见邻近设计） |
| 交付形态 | “出报告”“按品牌分组”“先给 6 台” | manifest/报告/增量 |

**输入不统一是常态**：一句话里可能同时有 4–5 类信息，也可能只有类目。解析器的目标不是“猜全”，而是**把能确定的确定下来，把不能确定的显式标成缺省/待确认**。

## 2. TaskSpec：建议的任务单结构（不是现有 brief 的替代，而是它的上游）

```json
{
  "task_id": "t-20261115-001",
  "class":       {"value": "沙漠牵引车", "source": "user", "confidence": 0.95},
  "quantity":    {"primary": 10, "backup": 4, "source": "user"},
  "brands": {
    "include": ["陕汽", "中国重汽"],
    "exclude": ["北奔"],
    "foreign_ratio": {"min": 0.2, "max": 0.4, "source": "user", "strict": false}
  },
  "models": {
    "pinned":   [{"model": "H6066 6×6", "source": "user"}],
    "provided": [{"model": "X3000", "image": "upload/xx.jpg", "source": "ocr", "confidence": 0.8}]
  },
  "constraints": {"views": ["front"], "exclude": ["挂车", "内饰"], "min_width": 800},
  "scope":       {"mode": "mixed", "ratio": {"exact": 0.8, "adjacent": 0.2}},
  "delivery":    {"format": "report", "incremental": true},
  "assumptions": ["未指定年份，按现行款处理"],
  "unknowns":    ["外国品牌占比没有硬性口径，按宽松约束处理"]
}
```

要点：
- **每个字段带来源**（user / ocr / default / inferred），冲突时以 user 为准；
- `foreign_ratio`/`brand_quota` 保持**软约束**（排序/补位优先 + 交付披露）；“只要/必须进口”走 `constraints.origin`（硬），**不把占比做成硬配额**（2026-11-15 拍板）；
- `pinned` 是硬约束（必须占用槽位），`provided` 是证据（先验证再决定是否引用）；
- `unknowns` 显式记录“没问清楚”的东西，交付时可以提示，而不是偷偷替用户决定。

## 3. 从输入到任务：解析流水线

```
原始输入（文本/图片/文件）
  → 归一化（去噪、单位、数量表达）
  → LLM 结构化（TaskSpec JSON，few-shot + schema）
  → 规则校验（数量范围、品牌/型号格式、冲突）
  → 歧义处理（缺省 / 一次澄清）
  → 生成 brief（现有 v3 schema + scope 等扩展）
  → 规划（S1：查询 + 型号池 + 配额）
```

### 3.1 文本输入

- LLM 一次调用输出 TaskSpec；提示里给 3–5 个“混乱输入 → TaskSpec”示例；
- **规则校验**：数量 1–50；`backup ≤ primary`；品牌必须是“品牌词”而不是型号（用 `identity` 的码规则反向排除）；`pinned` 的型号必须可解析出主码或至少品牌+车系；
- **冲突**：`include` 与 `exclude` 同一品牌 → 以 exclude 为准并提示；`foreign_ratio` 与 include 冲突 → 以 include 为准；
- **缺省**：数量默认 10/4（可改）；视角默认不限；质量默认 ≥800 宽（只告警）。

### 3.2 图片输入（用户给图 + 型号）

**主路径（2026-11-15 拍板）：用户图不经过检索流程。**

```
用户输入（图 + 车型信息）
   ├─ 有有效车型信息 → 按完整程度判 A/B/C → 额外交付 + 与抓取图一起进分析
   └─ 没有有效信息   → 补问一次；不交付、不分析（可留作参考图）
```

- **有效车型信息**：用户文字优先、图上 OCR 次之；能解析出型号主码（`identity.primary_code`）或品牌+车系即算有效；都拿不到 → 只问一次（BC-S01-009）；
- **判级（只标注、不淘汰）**：复用门卫本地标签（`scene` + 分辨率）。A = `single_vehicle` 且长边 ≥1200；B = 整车且 ≥800，或 `part` 且 ≥1200；C = 多车/局部且 <800、或车型信息弱；
- **额外交付**：`user_delivery.extra` 的 `U1..Un`，每条带 `grade / source=user / model`；**不计入** N 主 + 4 备、交付率、confirmed；分析报告里与检索证据**分开统计**；
- **不做**：不占检索槽，不进 plan/fetch/verify；只按 sha1 提示“与已交付重复”，不进检索去重键。

仍有效的旧规则：文本只有“(图)”没有真图 → 要求补图（BC-S01-009）；`provided` 里 `model` 为空的条目要过滤（BC-S01-013）。

### 3.3 输入 → 规划的映射

| TaskSpec | brief / plan / engine |
|---|---|
| `quantity` | `page_budget.vehicle_slots/backup_slots` |
| `brands.include` | 规划阶段生成品牌覆盖查询（用户给的品牌是输入，不是词表） |
| `brands.exclude` | `negative`/查询负词 + 交付过滤 |
| `foreign_ratio` | 排序/补位软约束；需要“品牌国别”信号（见 §5 开放问题） |
| `models.pinned` | `plan` 的 `pins`（锁定占槽） |
| `models.provided` | 先验证；通过后作为 `pins` 或参考图 |
| `constraints.views/quality` | 查询后缀 + 门卫过滤 + 排序 |
| `scope` | 邻近设计（`adjacent-scope-design`） |
| `delivery` | manifest/报告/增量 |

## 4. 冷启动评估（S0-03）与 DeepSeek 能力

### 4.1 专家主张

“用户只给品类词时，LLM 用**参数化领域知识**直接生成基础型号池（不联网），再在召回中动态补全。”
这和我们的“候选必须来自检索结果”冲突；需要实测它到底是“知识”还是“幻觉”。

### 4.2 V6 探针（已跑）

- 脚本：[`scripts/probe_cold_start.py`](../scripts/probe_cold_start.py)
- 数据：[`data-test/evals/cold-start-probe-20261115.json`](../data-test/evals/cold-start-probe-20261115.json)
- 方法：10 个类目 × 最多 8 个型号，`deepseek-flash` 生成 → 每个型号发一条搜索 → 标题/摘要是否出现该型号主码（复用 `identity` 归一化）→ 与三轮真实检索池比对。

**结果**：

| 指标 | 数值 |
|---|---|
| 提出型号 | 65（部分类目未给满 8） |
| 搜索可证实 | **56（86.2%）** |
| 与我们三轮检索池重合 | **5（7.7%）** |
| 分类可证实率 | 拖拉机/叉车/压路机/清障车 8/8；沙漠牵引车 3/3；搅拌车 6/8；**消防车 2/6**；扫路车 4/6；随车吊 4/5 |

**解读**：
1. **不是大面积幻觉**：86% 能被搜索证实，说明 flash 对主流工程车型有真实知识；
2. **但和我们的池几乎不重合**：它给的是**公告型号**（如 `SX2150`、`XGF5160GXFPM50`、`Kalmar DRG450`），我们抽取的是**商业名称**（“陕汽德龙X3000”）。这恰好是补充价值：我们不会主动搜公告型号；
3. **专业类目衰减**：消防车/扫路车的公告型号大量“搜不到”，说明知识密度随细分下降，不能当权威；
4. **不能直接当池**：14% 不可证实、且型号可能对应多个上装/年款；必须过检索与去重。

### 4.3 结论：只做“查询种子层”

建议新增 `ColdStartSeeder`（S0→S1 之间，可选、默认关）：

1. LLM 生成 5–8 个种子（品牌+型号/公告型号），标注置信；
2. 每个种子生成 1 条查询（`品牌 型号 类目`），走现有搜索；
3. **证据门槛**：结果标题/摘要出现该型号主码或品牌+车系 → 记 `seed_verified`，进候选池；否则丢弃并记录 `seed_unverified`；
4. 预算：每类目 ≤8 条查询（约占一轮 50 条的 16%），只在新类目/池 short 时启用；
5. 产物：`plan.seeds`、`plan.seed_rejected`，可审计；不影响现有候选来源规则。

### 4.4 DeepSeek 能力判断

- **flash（现用）**：足以做“种子生成”（86% 可证实）；不适合做“权威型号池”（14% 不可证实、专业类目弱、年款/配置不可靠）；
- **更大的模型**（如计费表里的 `v4-pro` 档）：可能提升细分召回，但成本约为 flash 的 4–5 倍（输出 ¥27 vs ¥8 / 百万 tokens），而**仍然需要检索验证**；建议只在“消防/扫路等知识薄弱类目 + 池 short”时试用，先做 A/B；
- **真正决定质量的是“验证”而不是“参数”**：同一个种子，有检索证据就可用，没有就丢——这比换更大模型更稳。

## 4.5 V8 初测（临时原型，2026-11-15）

> 临时资产：`tmp/s0-probe-20261115/`（gitignored，**未入库**；再次启用需产品负责人同意）。
> 20 条输入 = 10 条历史 `request.raw`（来自 `p8-idmatch-20261114` 冻结 brief）+ 10 条合成变体
> （含外国品牌比例、指定品牌/车型、带型号图片、排除项、邻近参考、修正类“再加两台”）。
> 解析器为一次性原型：`deepseek-flash` + TaskSpec 子集 schema。

**结果（按人工期望核对）**：

| 维度 | 结果 |
|---|---|
| intent（new_task/modify/question） | **20/20** |
| 数量 primary | **19/19**（有明确数字的） |
| class（语义） | **19/20**（1 条把“单钢轮”拆进了 config） |
| 品牌 include/exclude | **5/5** |
| 视角/排除/指定车型/带图 | **6/6** |
| 邻近参考（scope） | 1/2（“再加两台”被当成新任务的数量） |
| 传动构型 | 9/10（叉车写成“四轮”，不是错误，是粒度不同） |
| 型号部件 | 10/10 语义命中（字面召回约 0.5，因为“挡泥板”vs“翼子板与轮拱”这类同义） |

**暴露的 4 个 schema 缺口（比准确率更重要）**：

1. **class / environment 混写**：解析器把“（仓储物流工况）”“市政道路/园区清扫工况”塞进 class，
   6/20 出现；根因是 TaskSpec 没有独立 `environment` 字段 → **必须拆开**；
2. **modify 语义**：“上次那批不行…再加两台”被解析成 `quantity.primary=2`，正确应是
   `delta=+2`；需要区分 `new_task` 与 `modify` 的字段语义；
3. **软/硬偏好**：“最好有齐格勒/卢森堡亚这种进口的”被写成 `brands_include`（硬约束），
   实际是软偏好；需要 `preferences.soft[]` 与 `brands_include`（硬）分离；
4. **同义/子类**：“随车吊”vs“随车起重运输车”、“压路机+单钢轮”vs“单钢轮压路机”，
   需要一个**受控的 class 规范化步骤**（不是词表：用 brief 生成时的 class 作为主名，
   其余作为 alias 记录）。

**结论**：S0-01 原型可用（意图/数量/品牌/图片输入都稳），但不能直接进生产；先补 TaskSpec v0.2
（environment、delta、soft preference、class canonicalization），再做 V8 正式基准（≥50 条，
含破坏性修正与多轮）。临时输入与参数不得写入正式代码或默认值。

## 5. 多轮输入与歧义（S0-05；S0-06 已归档）

- **多轮（S0-05，已采纳）**：见 S4 的 session/router（`session_router.py`：LLM 提议 + context + 守卫 + 歧义提问）；输入层只负责把“改口”转成 patch（TaskSpec diff），不重跑全解析；
- **歧义**：只对**破坏性**操作（删/替换/覆盖品牌）与**硬约束冲突**做一次澄清；其余用默认 + 在交付里提示假设；
- **能力边界（S0-06，2026-11-15 归档）**：**不在 S0 做准入判断**——弱交付是供给现实（E64 三轮 degraded 58.5%、交付 269/270），前置拦截会把本可交付的结果挡掉；改为**交付时透明标注**（证据等级 / 预期缺口 / 替代建议），条目移交 S3-05（仍待评）。
