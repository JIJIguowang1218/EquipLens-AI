## 1. 各轮实验（目的 / 设计 / 数据 / 结论）

### 1.1 A/B v1：skill v0.1 vs 无 skill（8 案例）

- **目的**：验证"按纪律产出清单"是否比自由发挥更好。
- **设计**：2 arm × 8 个车型类别（沙漠牵引车/重型吊车/随车吊/高空作业车/装载机/搅拌车/宽体矿卡/压缩垃圾车）；每 arm 拆 2 个隔离 subagent，各跑 4 例；判据预注册（六维：口径构型、结构事实、部件轴、理由可审、必要确认、诚实度）。
- **数据**：

| 指标 | A（无 skill） | B（skill v0.1） |
|---|---:|---:|
| 交付槽位 | 89/96（92.7%） | **5/96（5.2%）** |
| 六维均值 | 5.875 | 6.000 |
| 硬错误 | 1（低置信档案仍给 9 个推荐） | 0 |
| schema 通过 | 自由格式 | 8/8 |

- **结论**：B 的纪律在冷启动类目上变成死结——`inference 未验证不得进推荐` + 无档案/无名录 ⇒ 推荐位恒为 0。
- **评审意见（产品负责人）**："指标是占槽就行吗？我觉得 skill 是否有效不是要看选出来的车型是否更有关联吗。"

### 1.2 A/B v2：`provisional` 档（修死结）

- **改动**：方向级目标可占槽（须 `verify_by`）；判断脚本与分配器分工；判据换 `fill_rate` 主指标。
- **数据**：82/96（85.4%）；硬错误 0；schema 8/8；六维 5.50（A 5.875）。
- **新问题**：**89% 的槽是方向级**（73/82），真正确认到车型只有 9 槽（9.4%）——"填得满，填的是方向"。
- **评审意见**："为什么允许方向的出现，没有车型下一步爬取什么？这不就是需要你分析方向给出车型推荐。"

### 1.3 相关性评测（3 案例、65 条盲标）

- **设计**：两臂候选并集 + 陷阱项；标 2（直证）/1（类比）/0（陷阱）；算车型精确率、直证数、层覆盖、陷阱率。
- **数据**：

| 指标 | A | B |
|---|---:|---:|
| 车型精确率 | 100% | 100% |
| 直证（label=2） | 19 | 18 |
| 层覆盖（exact/environment/platform） | 9/9 | **6/9** |
| 陷阱被提出 | 0 | 0 |

- **结论**：skill 没有让选车更准；B 因 `allow_cross_vehicle=false` 把平台/跨车型层压进 backlog，覆盖反而更差。
- **方法学教训**：首版评分器要求"申报串每个词都出现在标题"，把 A 的"中国重汽 豪沃 6X6…"误判为不成立（6/12）；改为以索引条目为锚点后 11/12。**字符串匹配本身会制造假差异。**

### 1.4 证据层（v0.3）：清单必须带 URL

- **设计**：`evidence{url,title,grade,source}`；recommended 必须 E3（标题含型号的详情页）；12 台硬要求；弱关联尾巴标 `weak`。
- **数据**：A/B 各 12 台，证据有效 **11/12（92%）**，强/弱 7/5，陷阱 0/0；两臂唯一不成立的都是北奔 NG80（页面标题无 NG80）。
- **结论**：**证据基础设施把两臂一起拉高，skill 分差被抹平**；差异只剩标注方式（B 把北奔降 provisional、纯方向进 `next_action`）。

### 1.5 实图核对（文字层验不出的东西）

- **动机（产品负责人）**："直接用这次的 A、B 清单分别去爬取图片…这是在文字层面永远验不出来的，也是我们测试一直忽略的。"
- **首轮暴露**：百度图片 acjson 返回 `antiFlag:Forbid spider access`、HTML 跳安全验证；Bing 返回壁纸/梅西类无关内容；`gate.py` 门卫**未被调用**（且 `uform` 未安装）。结果：内饰、局部结构、错车型、"解放战争"混入。
- **修复（都在模块内）**：
  1. 新增 **360 图片**通道（本环境唯一可用）；
  2. `_relevant()` 护栏 v2：非车词拒（战争/壁纸/车模…）、型号代码优先、**构型必须一致**（6x6≠6x2）、品牌必须出现；
  3. 通道状态 `ok/empty/blocked` 回传，不再静默；
  4. 查询阶梯（型号+工程车 → 型号）；
  5. `gate.check_exterior()`：整车主图 = 门卫放行 + 视角 ∈ {hero_45, side, front, rear}；部件页仍用 `check()` 保留特写。
- **结果**：105 判定 → 70 张保留（detail 19 / interior 3 / 门卫拦 13）；23 车型、22 个有图。
- **人工核对结论（产品负责人 10-31）**：目测"大部分准确、没什么问题"，**记为合格待测**（不逐条打分）。
- **评审意见**："门卫怎么设计的，怎么还有内饰、局部结构等等看不出来是卡车外观的内容？" → 已修，并明确"视角留给交互，不塞给模型"。

## 2. 为什么 skill 被毙（四条硬证据）

1. **判断不增量**：相关性 100% vs 100%、直证 19 vs 18、证据有效 11/12 vs 11/12——三轮不同口径都打平。
2. **可用性曾经更差**：v0.1 交 5/96；v0.2 靠方向撑到 85%，真实车型只有 9.4%。
3. **价值被基础设施覆盖**：真正把质量拉起来的是**证据索引**（E3 门槛）和**图片通道/门卫**，不是那六条纪律。
4. **约束反噬**：`allow_cross_vehicle=false` + 平台层默认备选，让 B 的层覆盖只有 6/9。

## 4. 复盘：三次同类错误（值得写进仓库规矩）

1. **口径错位**：把"占槽率"当质量（v1/v2），被产品负责人纠正 → 质量指标必须是"选得对不对"。
2. **绕行**：图片被抓坏时，我改成"从证据页抓图"，绕开 `imagesearch` → 被纠正；正确做法是修模块（加通道、加护栏、接门卫）。
3. **规则替代验证**：用 `provisional` 让方向占槽把指标做漂亮 → 掩盖了"没有车型"的事实。

三条可复用规矩：

- 指标必须直接对应交付物（车型/图），不能用过程量顶替；
- 测试只能调用生产模块，不得在测试脚本里另起策略；
- 指标变好看但交付物没变，视为回归。
