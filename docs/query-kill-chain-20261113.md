## 0. 结论速览

- 第二段“判死”不是单一 bug，而是一条对**命名风格敏感**的链路：车名越像“一句描述”，越容易被丢弃。

  - 查询键：1135 个历史车型，76 个“型号码只在括号里”的全部修好；378 个超长查询里 311 个变短；
  - 相关性护栏：4337 条可回放命中中，**旧放行/新拒绝 = 0**（无回归）；
  - 身份证据：4456 个历史 unknown 资产中 382 个（8.6%）可凭“车系+构型”双证据升级。
- 类目词表方案**作废**；替代方案见 §4。

## 2. 全局评估：为什么按这个顺序

1. **先修“确定性解析”**（#3/#4/#5）：不涉及阈值、不会误放行，收益直接且可回放；
2. **再修“身份证据”**（#6/#7）：影响 accepted，需离线抽样核对；
3. **最后才谈阈值/策略**（来源降权、tier 规则）：前两步没有稳定前，调阈值会掩盖问题；
4. **门卫/视角不动**：已有 17752 次 low_resolution 只是 warning，`wrong_config` 仅 85 次，
   不是当前瓶颈；动它只会引入新的误杀。

## 4. 去表化替代方案（类目词表作废）

### 4.1 来源规则（不查类目词）

wide 抽取在 c2 混进的 4 台离类车，**全部只被 `environment` 维度查询发现、只有 1 个来源**。
因此规则可以是：

> 候选必须至少 1 条来自 `base`（由用户输入类目/工况构建）的来源；只有 `environment`/`topup`
> 来源的候选降权到 pool 尾部，不删除。

这是“来源证据”，对任何类目成立；不用枚举“正面吊/reach stacker”。

### 4.2 身份证据（不查品牌表）

- confirmed：型号码命中标题；
- probable：**拉丁车系 + 构型**双命中，或 2 个非通用中文片段命中，或中文片段 + 构型；
- 单品牌词命中**不算**（反例：`HOWO 6×6 全驱牵引车` vs 标题 `HOWO TX 牵引车` 是不同车型）；
- 品牌表保留为“额外加分”，不再是门槛。

| 指标 | 数值 |
|---|---:|

抽样（人工核对片段）：`德龙 X3000` ← 标题“陕汽德龙x3000自卸工程车” → confirmed（正确）；
`Oshkosh J-3080 6×6` ← “oshkosh mk23 … 6x6 cargo truck” → probable（正确）。
**仍存误接受风险**：`解放 J5M` 这类“同品牌不同型号”可能凭品牌加分升 probable，
因此本轮只加“车系+构型”双证据，不加“单品牌词”。

### 5.4 口径与局限（必须写明）

- `fetch_log` 只记录“当时通过护栏”的命中，因此回放**无法测量历史上被静默丢弃的量**；
  “旧拒绝→新放行 85”说明历史日志里存在用当前旧实现会拒的行，属于版本漂移，不是严格 A/B；
- 身份回放是“历史存储的 identity（旧代码产出）” vs “当前 verifier”，382 个翻升包含版本差异；
- 离线回放只验证判定层，**不等价端到端交付**；端到端需另跑 loop（未跑）。
