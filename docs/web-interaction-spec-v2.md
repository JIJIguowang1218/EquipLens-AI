## 0. 一句话

**从"说出看什么设备"到"拿到一页页可编辑的竞品分析"，中间只有四个动作：说、筛、选、排。界面围绕这四个动作，而不是围绕系统的内部步骤。**

---

## 1. 设计立场（三条，先于一切细节）

1. **界面是工作台，不是向导。** 不做"下一步"式的多步弹窗；进度用一条始终在场的测量轨（见 §3.4）表达，用户随时知道自己在第几段、还要多久。
2. **等待必须产信息。** 任何超过 3 秒的等待，屏幕上必须有东西在长出来（查询日志、证据条数、逐行填充的表格）。不做转圈，不做"请稍候"。
3. **纸与墨分家。** 应用外壳是墨（近黑），成品页面是纸（近白）。用户永远能一眼分清"我在编辑"和"我在看成品的这一页"。

---

## 2. 页面模型：五个界面，七个状态

### 2.1 先回答你的划分问题

你提的是 7 个页面：开始 → 检索等待 → 结果筛选 → 分析等待 → 框选 → 排版等待 → 结果导出，判据是"版面出现很大的布局和交互变化就算一个界面"。

**这个判据方向是对的，但少了一条，会导致把"等待"也算成页面。** 一条更稳的判据是三个测试，三个都"变了"才配叫一个新界面：

| 测试 | 问什么 | 等待态为什么不过 |
|---|---|---|
| ① 对象变了没有 | 用户心里盯着的那个"东西"换了吗 | 没换——还是"这一次检索" |
| ② 主动作变了没有 | 这一屏主要让他做什么 | 没变——只能等，或取消 |
| ③ 空间模型变了没有 | 布局是否必须重排 | 没变——数据在原位长出来 |

等待屏三条全不满足，它是**状态**，不是**界面**。

### 2.2 独立等待页的代价（实测过的坑）

- **返回键歧义**：用户按返回，是回到输入，还是回到"上一次等待"？多出来的页面会让浏览器后退变成抽奖。
- **刷新恢复**：每个页面都要存一份恢复点，7 个页面就是 7 处状态机；出错时最难查的就是"页面回来了但数据没回来"。
- **演示节奏被打断**：评审看片时，连续三个"只有进度条"的页面会把 100 秒的注意力切碎。
- **空转页没有出路**：卡在等待页时，用户除了盯着看，没有任何可用动作。

### 2.3 结论：五界面 / 七状态

```
S0 立项台 ──▶ S1 检索台 ──▶ S2 素材台 ──▶ S3 编排台 ──▶ S4 交付台
   输入        检索→筛选      选车→分析      框选→排版      预览→导出
              (retrieving)   (analyzing)   (composing)    (exporting)
```

| 界面 | 路由 | 主对象 | 主动作 | 含等待态 | 时间预算 |
|---|---|---|---|---|---|
| S0 立项台 | `/` | 一次意图 | 说清看什么 | — | 0–60s（人的时间） |
| S1 检索台 | `/r/:id/retrieval` | 候选车型清单 | 勾选与增删 | `retrieving` | 10–60s |
| S2 素材台 | `/r/:id/materials` | 每台车的主图 | 采用/换图/上传 | `analyzing` | 30–120s |
| S3 编排台 | `/r/:id/compose` | 一页 16:9 成品 | 框选与微调 | `composing` | 20–40s/台 |
| S4 交付台 | `/r/:id/delivery` | 交付物 | 确认并导出 | `exporting` | 3–10s |

**你的 7 项映射**：开始页→S0；检索等待+结果筛选→S1 的两个状态；分析等待→S2 的 `analyzing`；框选→S3 的「框选」模式；排版等待→S3 的 `composing`；结果展示确认导出→S4。

> 如果一定要有"翻页感"：等待态用**整屏 morph**（提交按钮长成进度轨、输入框收成角标），视觉上像换了一页，路由上没换。这是本规格里最重要的一条实现约定。

## 3. 视觉系统

### 3.1 颜色：只有墨、纸、灰阶，加一个"错误红"

| Token | 值 | 用途 |
|---|---|---|
| `--ink` | `#0B0B0C` | 外壳底色 |
| `--ink-1` | `#121214` | 面板 |
| `--ink-2` | `#17171A` | 抬升/悬停 |
| `--line` | `rgba(242,241,238,.13)` | 1px 分隔线（主角） |
| `--line-2` | `rgba(242,241,238,.06)` | 次级网格线 |
| `--text` | `#F2F1EE` | 正文（纸白） |
| `--text-2` | `#9A9A95` | 次要 |
| `--text-3` | `#6A6A66` | 占位/刻度 |
| `--paper` | `#F4F2ED` | 成品页面底色 |
| `--paper-ink` | `#141414` | 纸上的字 |
| `--fail` | `#C4473C` | **仅**错误与阻断，不做装饰 |

**不用颜色编码状态。** 通过＝实心纸白块，待定＝1px 描边，失败＝斜线纹理（hatch）。这套"填充/描边/斜纹"代替红黄绿，是本产品的识别点，也顺带解决色弱可用性。

### 3.2 字

- 正文/界面：`Inter` → `"HarmonyOS Sans SC"` → `"PingFang SC"` → `"Microsoft YaHei"`
- 数字/型号/ID/计数：`IBM Plex Mono` → `"JetBrains Mono"` → `monospace`（型号 `NG80`、`6X6`、时长、百分比一律等宽，字距收紧 −0.01em）
- 字号阶梯：`96 / 56 / 32 / 22 / 16 / 13 / 11`（11 只用于刻度与标签，全大写 + 0.08em 字距）
- 标题行高 `0.92`，正文 `1.55`；大标题字距 `-0.03em`

### 3.3 网格与形状

- 12 列，24px 槽，页边距 40px；左测量轨 64px（见 3.4）
- 圆角只用 **2px**（输入框、按钮、卡片统一）——工程图纸的直角感，区别于默认的"大圆角卡片"
- 阴影几乎不用；层级靠 1px 线和底色差
- 图片统一 1px 描边 + 四角裁切标记（crop marks），这是"框选"这件主业务的视觉母题

### 3.4 签名元素：左侧测量轨

一条 64px 宽的竖向刻度尺，贯穿所有界面：

```
┌──┐
│00│ ← 当前段，实心反白
│──│
│01│
│──│
│02│
│──│
│03│
│──│
│04│
└──┘
```

- 已完成段：纸白细线；当前段：反白块 + 段号；未到段：`--text-3`
- 悬停显示段名与"回到这一步"（已完成的段可点回去）
- 运行中，当前段右侧出现一条 1px 的竖向进度线，按真实进度增长

### 3.5 动效原则

| 场景 | 时长 | 缓动 |
|---|---|---|
| 悬停/按下/聚焦 | 120ms | `cubic-bezier(.22,1,.36,1)` |
| 状态切换（勾选、采用、展开） | 240ms | 同上 |
| 界面内布局重排（表格→检查器） | 420ms | 同上 |
| 跨界面 morph（提交→检索台、确认→编排台） | 680ms | 同上 |
| 退场 | 180ms | `cubic-bezier(.4,0,1,1)` |

- 只动 `transform / opacity / clip-path`，不动 `width/height/top`（除非是网格重排）
- `prefers-reduced-motion` 下全部降为 0ms 淡入
- 同一时刻最多一条主动效线；不做多层并行动画

## 4. 全局骨架

```
┌64┬──────────────────────────────────────────────────────────────────┐
│  │ 顶栏 56px：面包屑（类别 · 台数）        进度文案      [运行 00:42]│
│测├──────────────────────────────────────────────────────────────────┤
│量│                                                                  │
│轨│                        当前界面主体                              │
│  │                                                                  │
│  ├──────────────────────────────────────────────────────────────────┤
│  │ 底栏 64px：主按钮（右） · 次按钮（左） · 状态句（中）             │
└──┴──────────────────────────────────────────────────────────────────┘
```

- **顶栏**：面包屑只写"类别 · N 台"；右侧是运行计时与"取消"（仅运行中）
- **底栏常驻**：每个界面只有一个主按钮（实心纸白），次按钮描边；状态句是一句人话（"4 台已选，1 台缺证据"）
- **右侧检查器**：S1/S2 各有一个 320–360px 的右栏，随选中项变化；S3 的右栏是槽位，S4 的右栏是导出
- 1280 起可用，1440 为主设计宽度；<1280 折叠右栏为抽屉；<1024 不在本期范围

## 5. S0 立项台

**目的**：把一句人话变成结构化意图，并让用户对"将要发生什么"有预期。

```
┌64──────────────────────────────────────────────────────────────────┐
│00  EquipLens                                      最近 ▸ 3 条历史   │
│                                                                    │
│   看什么设备？                                                      │
│   ┌────────────────────────────────────────────────────────────┐   │
│   │ 沙漠牵引车                                          ↵ 开始  │   │
│   └────────────────────────────────────────────────────────────┘   │
│                                                                    │
│   牵引车 ×  前脸 ×  格栅 ×  保险杠 ×  轮眉 ×      台数  − 3 ＋      │
│                                                                    │
│   将检索 12 篇来源 · 约 40 秒 · 自动抓图（可关）        ⓘ 高级设置  │
└────────────────────────────────────────────────────────────────────┘
```

**内容与控件**

| 元素 | 说明 |
|---|---|
| 大标题 | 56px，"看什么设备？"；每 8s 轮换一次示例副标题（不喧哗，只在输入框下方淡入） |
| 主输入 | 单行，32px 字；占位符给真实样例（"沙漠牵引车""重型吊车""8×4 自卸车"） |
| 解析 chips | 输入停顿 300ms 后解析：`类别` `部件` `台数`；chips 逐个 60ms 错峰淡入；可点 × 删除，删除即纠错 |
| 部件多选 | chips，默认 前脸/格栅/保险杠/轮眉/踏步；点开弹出词表（可搜索） |
| 台数步进 | `− 3 ＋`，范围 1–12；演示默认 3 |
| 素材来源 | 分段控件：`自动抓图` / `我自己上传`；默认自动 |
| 最近 | 右下角只放 3 条（不抢首屏），点开直接进该 run 的对应界面 |
| 主按钮 | 输入框右侧内嵌"↵ 开始"，输入框为空时降为 40% 不透明度 |

**状态**

| 状态 | 表现 |
|---|---|
| 空 | 占位符 + 一行灰字说明；主按钮禁用 |
| 解析中 | chips 位置留空 24px 高，不抖动 |
| 解析成功 | chips 落位；底栏状态句"将检索约 12 篇来源" |
| 无法识别类别 | 不阻断：chips 显示"未识别"，底栏提示"将按通用目录检索，结果可能偏泛"，仍可开始 |
| 历史为空 | 最近区不显示，不留空盒子 |

**动效**：提交 → 输入框整行 `scaleY` 收到顶栏变成"类别 chip"，主按钮向左拉长成 64px 测量轨的 01 段（680ms），同时 S1 的查询队列从左侧滑入。

## 6. S1 检索台（含 `retrieving`）

> **2026-11-04 变更**：S1 静态稿已改为「卡片网格 + 右栏（关联分析 + 清单）」结构，产物见 `docs/ui-mock/s1.html`（`?s=start|mid|done`），文案契约见 §6.3。下面的 §6.1 / §6.2 三栏表格是 v2 原型，保留作对照；实现以静态稿与 §6.3 为准。

**目的**：让等待变成可读的过程；结果出现后，让用户在一屏内完成勾选。

### 6.1 `retrieving` 状态（前 10–60 秒）

```
┌64──────────────────────────────────────────────────────────────────┐
│01  牵引车 · 3 台           检索中 · 24s      ▓▓▓▓▓▓░░░░ 4/7 查询  ✕│
├────────────┬──────────────────────────────────┬────────────────────┤
│ 查询队列    │ 候选（逐行长出来）                │ 通道状态            │
│ ✓ 牵引车…  │ 德龙 X3000   ████████░ 3 篇       │ 360   12/12 相关    │
│ ✓ 牵引车…  │ 豪沃 4       ██████░░░ 2 篇       │ 百度   被拦（验证页）│
│ › 牵引车…  │ 解放 JH6     ███░░░░░░ …          │ Bing   0/12 相关    │
│ ○ …        │ 德龙 6X6     ░░░░░░░░░ …          │ 证据   34 篇         │
└────────────┴──────────────────────────────────┴────────────────────┘
```

- 左：查询队列，逐条从 `○` 变 `›` 变 `✓`，被拦的标斜纹并附一行原因
- 中：候选行骨架 → 每找到一个车型就补一行，行内三条细条表示"提及/证据/图片"的进程
- 右：通道状态（360 / 百度 / Bing），**如实显示被拦**——这是产品诚实性的展示窗口，不要藏
- 底部：`已 34 篇来源 · 6 台候选`；`取消` 在顶栏

### 6.2 `ready` 状态（结果筛选）

```
┌64──────────────────────────────────────────────────────────────────┐
│01  牵引车 · 3 台            6 台候选 · 34 篇来源        [重新检索] │
├────────────┬──────────────────────────────────┬────────────────────┤
│ 品牌 全部  │ ☑ 德龙 X3000   陕汽  12 篇  E3    │ 证据（选中行）      │
│ 构型 6×6   │ ☑ 豪沃 4       重汽   9 篇  E1    │ ① 车型大全…         │
│ 证据 E3    │ ☐ 解放 JH6     一汽   7 篇  E3    │    URL · 摘要       │
│ ─────────  │ ☑ 德龙 6X6     陕汽   5 篇  T3    │ ② 推荐…             │
│ ＋ 手动添加 │ ☐ 三一 STC…    三一   3 篇  T3    │ 关联理由（可改）    │
├────────────┴──────────────────────────────────┴────────────────────┤
│ 已选 4 台 · 1 台仅弱关联        ＋ 手动添加        [确认清单 →]     │
└───────────────────────────────────────────────────────────────────┘
```

| 元素 | 说明 |
|---|---|
| 左筛选栏 200px | 品牌 / 构型 / 证据等级三段；计数实时；"＋ 手动添加"常驻底部 |
| 表格 | 行高 56px；列：勾选 · 车型（等宽型号）· 品牌 · 来源数 · 证据等级 · 状态 |
| 证据等级 | `E3` 实心块、`E1` 描边块、`T3` 斜纹块；不解释缩写，悬停给一句话 |
| 右检查器 360px | 选中行的证据列表（标题 + URL + 摘要），关联理由可直接改 |
| 行内动作 | 悬停出现"看证据 / 移除"；无证据行整行降透明度，勾选框禁用 |
| 底栏 | 已选计数 + 阻断提示 + 主按钮"确认清单 →" |

**状态**

| 状态 | 表现 |
|---|---|
| 检索中 | 骨架 + 日志（见 6.1） |
| 部分成功 | 顶栏出现"2 个通道被拦"的斜纹 chip，点开看原因；主按钮仍可用 |
| 全被拦 | 中央一块"没有取到结果"的说明 + 三个出路：`重试`（换时段）、`只用手动录入`、`改查询词` |
| 无勾选 | 主按钮禁用，底栏句"至少选 1 台" |
| 弱关联被勾 | 该行出现斜纹描边，底栏"1 台仅弱关联，将在素材页优先复核" |
| 重新检索 | 二次确认浮层：说明会保留已勾选项（不清空） |

**动效**：勾选 → 行底色 120ms、右侧计数 240ms 数字滚动；切换选中行 → 检查器内容 240ms 交叉淡入，不整块重排。

### 6.3 关联分析文案（2026-11-04 定稿，跨阶段沿用）

S1 右栏顶部那段散文是**分析结论的陈述**，不是检索过程日志。高保真与接后端后，这段文字仍按本结构组织与生成。

**结构（四层，顺序固定）**

| 层 | 轴 | 写什么 |
|---|---|---|
| 1 | 精确类目 `exact` | 车型的基础形态（驱动形式、基型），以及哪些部件属平台通用造型件 |
| 2 | 环境特化 `environment` | 该工况下被特化的部件（防护栏、进气防护、底盘离地、踏步防滑），并说明**即使未被点名也属本类车型的设计特征** |
| 3 | 基型平台 `platform` | 前脸与驾驶室轮廓的继承关系；同平台车型用于印证家族关系 |
| 4 | 跨车型构型 `cross_vehicle` | 功能件（踏步、爬梯、把手）构型可跨车型比较，证据强度弱，只作备选 |

**写作约束（改稿时先对这几条）**

- 一段散文，不分点、不编号；专业书面语，陈述事实，不用"我们 / 系统 / 本次"作主语
- **不写**素材与放闸（"图片够不够""可裁部件不足"），**不写**检索先后（"先……再……"）
- 不解释术语，不写论文腔（"本体属……""是本次分析的精确对象""用来回答……"）
- 收尾一句交代跨车型层证据弱、仅作备选，与清单中两条虚线备选卡对应

**正本（版本 A，2026-11-04 采用）**

> 沙漠牵引车以 6×6 为基型，前脸、格栅与保险杠属平台通用造型件，不随工况变化。沙漠工况的特化落在防护栏、进气防护、底盘离地与踏步防滑上，这些部件即使未被点名，亦构成本类车型的设计特征。前脸与驾驶室轮廓承自基型平台，同平台车型可验证其家族关系。踏步、爬梯与把手为功能件，构型跨车型可比，证据强度弱，仅作备选。

## 10. 跳转、回退与恢复

| 从 | 到 | 触发 | 守卫 |
|---|---|---|---|
| S0 | S1 | 提交 | 类别非空 |
| S1 | S0 | 测量轨 00 / 面包屑 | 运行中先确认"取消这次检索？" |
| S1 | S2 | 确认清单 | ≥1 台已选 |
| S2 | S1 | 返回 | 已采用的图保留 |
| S2 | S3 | 开始分析 / 进入编排 | ≥1 台有整车图且分析完成 ≥1 台 |
| S3 | S2 | 返回 | 未保存的框选自动存草稿（1.5s 防抖） |
| S3 | S4 | 全部完成 | ≥1 页已生成 |
| S4 | S3 | 返回修改 / 点检查项 | — |

- **刷新恢复**：路由带 `runId`，前端从 `/api/run/:id` 恢复；任何界面刷新都回到该界面的当前状态，不回到 S0。
- **并发**：同一时刻只允许一个 run 在跑；再开新 run 时提示"有一个分析正在进行，先等它结束或取消"。
- **后退键**：浏览器后退 = 上一个界面（按上表反向），不进入"等待态"历史——等待态用 `replaceState`，不压栈。

## 11. 技术栈建议

### 11.1 结论

| 层 | 选择 | 为什么 |
|---|---|---|
| 构建 | **Vite 7** | 冷启动快、产物是纯静态、交给 FastAPI 托管即可 |
| 框架 | **React 19 + TypeScript** | ⚠️ 关键理由：DSH 侧边栏面板本身是 React 组件（`ctx.slots.register`），选 React 意味着 S3/S4 的面板将来能直接复用到 harness 里，不用写第二套 |
| 样式 | **CSS Modules + 设计 token（CSS 变量）** | 本规格的颜色/字号/间距全是精确值；不用 Tailwind 是为了避免"一看就是模板"的默认观感，也不用组件库（会和 3.1 的墨纸语言打架） |
| 组件 | 自建 + **Radix Primitives**（仅 Dialog/Popover/Tooltip/Select） | 只借无障碍与焦点管理，外观全部自绘 |
| 动效 | **Motion**（framer-motion 12）+ View Transitions API | 跨界面 morph 需要"共享元素"能力；纯 CSS 做不到布局重排的连续过渡 |
| 服务端状态 | **TanStack Query v5** + SSE | 轮询/重试/缓存开箱即用；进度走 SSE，比轮询省 |
| 本地状态 | **Zustand**（单个 store：当前 run 的草稿态） | 五个界面共享"这次 run 的临时改动"，比 prop drilling 干净 |
| 路由 | **React Router 7** | 5 条路由 + 守卫，够用；不用 Next（不需要 SSR，徒增部署复杂度） |
| 表单校验 | 原生 + **zod**（与后端 schema 对齐） | 一个表单不需要 react-hook-form |
| 图形 | 原生 `<img>` + **SVG 覆盖层**（框、把手、辅助线） | 框选是矩形与 8 个把手，不需要 canvas 库；SVG 天然清晰、可访问、易测 |
| 测试 | **Playwright**（5 条主路径冒烟） | 环境里已有，截图/交互都能录 |
| 部署 | `pnpm build` → `web/ui/dist`，FastAPI `StaticFiles` 托管 | 单端口、`start.bat` 一键起，不引入 Node 运行时依赖 |

**被否掉的**：Next.js（要 SSR/服务端路由，我们不需要）；Svelte（DSH 复用断掉）；Tailwind（速度换观感，本项目的辨识度是硬指标；若后期赶工，可作为局部补充）；Ant Design / shadcn（默认观感太强）；react-konva（框选用不上 canvas）。

### 11.2 目录与工程约定

```
webapp/
  src/
    app/            # 路由、守卫、Shell
    surfaces/       # S0..S4（每个界面一个目录：index.tsx + *.module.css）
    components/     # Button/Field/Chip/Table/CropFrame/Ruler/Progress...
    lib/            # api.ts(SSE) · schema.ts(zod) · format.ts
    styles/         # tokens.css · reset.css · type.css
  index.html
  vite.config.ts    # base:'/app/'  proxy:'/api' → 127.0.0.1:8770
```

- 组件只吃 token，不写魔法色值（CI 用一条 `grep '#[0-9a-f]\{6\}'` 卡住）
- 每个界面一个 `?mock=1` 的假数据入口，方便脱离后端调视觉
- 视觉回归：Playwright 对 5 个界面各截 1 张 1440×900 存 `docs/ui-shots/`
