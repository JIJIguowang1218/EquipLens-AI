# 商品/实体匹配调研 —— 工程车/重卡车型去重与 search_key 生成

调研日期：2026-11-14。仅网络检索（web_search / web_fetch），未跑实验、未改代码。
链接均已实际打开；仅凭检索摘要、未打开原文的条目会标注「未验证」。

## 0. 我们的四个落点（下文的「对应」列都指这四个）

| 步骤 | 含义 |
| --- | --- |
| 候选合并 | 从 N 条记录里**便宜地**捞出可能同款的候选对（blocking），不追求准，追求不漏 |
| 同类判定 | 对候选对做**贵一点**的打分/判定：是不是同一款车 |
| search_key 生成 | 从「一句描述」里净化出可检索的 key（去修饰、归并写法、拆出品牌/吨位/驱动） |
| 核验 | 抽样人工看 + 指标（pair completeness / precision）确认上面的改动是变好还是变坏 |

约束：不维护品牌/类目词表（无法穷举、伤泛化），因此下面**只收**「可从数据自举」或「通用语言学规则」的方案。

## 1. 方法清单

### 1) Splink —— Fellegi–Sunter 概率记录连接（无标注）
- 来源：https://github.com/moj-analytical-services/splink
- 原理：把「姓名/城市/日期」换成「品牌串/马力/驱动形式」，每个字段给出 m 概率与 u 概率，按对数似然比求和得到匹配权重；m、u 可以用 EM 与随机采样估出来，**不需要人工标注**，还支持词频（term frequency）修正与阈值聚类。
- 对应：同类判定（主力）；blocking rule 也可直接用于候选合并。
- 成本：低。纯 Python + DuckDB，笔记本百万级分钟级；我们量级（万级车型）秒级。
- 风险：README 明确说它不适合「单列 bag-of-words」——我们的输入恰好就是一句话。必须先在 search_key 生成阶段拆成 2–4 个伪字段，否则效果差；阈值与 m/u 需要按业务分布重估。

### 2) Dedupe —— 主动学习 + 自动学 blocking 规则
- 来源：https://github.com/dedupeio/dedupe ｜ https://docs.dedupe.io/en/dedupe_2/
- 原理：人只标几十对「像/不像」，库自动学出 blocking 规则与字段权重（logistic 回归），并提供 AffineGap、Jaro–Winkler、canonical 等多种字符串比较器，可自定义比较器与规则。
- 对应：候选合并 + 同类判定一体化；「自定义比较器」正是塞我们车型专用比较逻辑的入口。
- 成本：中低。几十条标注、单机可跑；但项目维护不活跃（文档停在 1.9.9 / 2020），依赖偏旧。
- 风险：需要少量标注；对中文需要自己接分词/字符 n-gram 比较器；训练出的规则人看不懂，排查成本高于 Splink。

### 3) RapidFuzz —— 字符/编辑距离与 token 集合打分的工程实现
- 来源：https://github.com/rapidfuzz/RapidFuzz
- 原理：Levenshtein/Jaro–Winkler/`partial_ratio`/`token_sort_ratio`/`token_set_ratio`/`WRatio`，C++ 实现、MIT。「一句描述」这类**长串包含短串**的场景，`partial_ratio` 与 `token_set_ratio` 比纯编辑距离稳。
- 对应：search_key 生成（归一化前后的一致性打分）+ 同类判定的 baseline（可以一天内上线）。
- 成本：极低。`pip install rapidfuzz`，无模型、无 GPU。
- 风险：README 示例写明 `token_set_ratio("fuzzy was a bear but not a dog", "fuzzy was a bear") == 100`——**子集即满分**。我们场景里「375马力 欧5」和「375马力 欧3」只差一个 token，会被判 100，必须补「冲突 token 惩罚」（数字/排放段单独硬校验）。

### 4) SC-Block —— 对比学习 embedding 做 blocking
- 来源：https://arxiv.org/abs/2303.03132（ESWC）
- 原理：用对比学习把记录映射到向量空间，最近邻搜候选对；论文在 99.5% pair completeness 下比 8 个 SOTA blocker 候选集更小，大规模商品数据集上流水线从 2.5 小时降到 18 分钟，训练约 5 分钟。
- 对应：候选合并（替代「按品牌首字分桶」这类脆弱规则）。
- 成本：中。需要 GPU 或 CPU 小模型（MiniLM 级）离线跑一次，之后是 ANN 检索；需要几百到几千对训练样本。
- 风险：要训练数据；embedding 对「375 马力 vs 380 马力」这类细粒度数字不敏感，只能当 blocker，不能当判定器；中文车型语料上需要重训。

### 5) WDC Products —— 三维度实体匹配基准（评估设计可直接抄）
- 来源：https://arxiv.org/abs/2301.09521（EDBT 2024）
- 原理：把匹配难度拆成三个正交维度——corner-case 比例、**测试集里训练集没见过的实体比例**、dev 集大小；同时给 pair-wise 与 multi-class 两种任务形式。结论：所有 SOTA 系统在「未见过的实体」上都明显掉点。
- 对应：核验（我们的评测集怎么切）。
- 成本：极低（只借方法论，不用跑它的数据）。
- 风险：英文商品数据，不能直接当我们的 benchmark；但它的切分维度（按车型/品牌留出、按 corner-case 分层）可以直接搬。

### 6) LLM 提示词做无监督商品匹配（GPT-3.5 级足够）
- 来源：https://arxiv.org/abs/2310.06174（Discover AI, 2024）
- 原理：在两个真实电商数据集上系统比较「便宜/简单的 prompt」与复杂 prompt 做产品匹配；结论是 GPT-3.5 已可用，且**更复杂更贵的 prompt 不一定更好**，并给了不同 prompt 之间输出一致性的分析。
- 对应：核验（高置信度对不用它；只把「规则打分在阈值灰区」的 1–5% 送 LLM 判），或给 search_key 生成做一次离线批量清洗。
- 成本：中。按灰区比例计费，可控；离线批量而非在线。
- 风险：输出不稳定（论文专门测了 inter-consistency）；不可审计；数字/型号幻觉。只能做「辅助+抽样复核」，不能做唯一裁判。

### 7) cleanco —— 闭类后缀剥离（词表最小化的范式）
- 来源：https://github.com/psolin/cleanco
- 原理：用一份**闭类**词表（Ltd./Corp./GmbH 这类法人后缀）把公司名剥成 base name，还支持传自定义词表。它的关键启发不是词表本身，而是：**只对「闭类功能词」建表，不对「开放类实体词（品牌）」建表**。
- 对应：search_key 生成——剥掉「卡车/牵引车/载货车/全轮驱动/欧5」这类闭类修饰；品牌不当词表，而当「从数据里自动挖的高频共现片段」。
- 成本：极低。规则代码 <100 行。
- 风险：直接搬英文后缀没用；必须改成「从语料里按频次自动挖闭类词」（见第 3 节 A），否则又回到维护词表的老路。

### 8) pypinyin —— 中文侧的音近/首字母归一
- 来源：https://github.com/mozillazg/python-pinyin
- 原理：汉字转拼音，支持多音字、首字母风格（`Style.FIRST_LETTER`）、自定义词组词典与自定义单字读音；可用 `load_phrases_dict` 修品牌专名。
- 对应：search_key 生成（同音错别字、简称/首字母缩写如「潍柴」→「WC」）。
- 成本：极低，纯 Python。
- 风险：**解决不了中英跨语言**（「卡特彼勒」↔「Caterpillar」靠拼音无解，那是别名表/翻译问题）；多音字在品牌名上易错，需要自定义词典兜。是否真能提升我们的召回：未验证。

## 2. 「无标注数据下怎么评估」——三条可落地的做法

1. **pair completeness + reduction ratio**（SC-Block 用的口径）：blocking 只要「不漏」，不需要标注——人工标 200 对候选里的正例即可估 recall 下界。
2. **留出实体而非留出对**（WDC Products 的核心）：按车型/品牌整簇留出测试集，否则同款的不同写法会同时出现在训练和测试里，指标虚高。
3. **一致性代替准确率**（论文 6 的做法）：同一批灰区对用两种不同 prompt/两种阈值各跑一遍，看结论冲突率；冲突率高说明这批样本本来就模棱两可，应进人工队列而不是硬判。

## 3. 最值得先试的 2 条

**A. 闭类词自动挖掘 + 槽位化 search_key（纯规则，零模型、零品牌词表）**
- 做法：对语料做字符 n-gram 频次统计，把「出现在 >X% 记录里、且位置分散」的片段判为闭类修饰词（卡车/牵引车/驱动/欧5/马力），剥掉后剩下的高频片段即候选品牌/车系；数字与单位（马力、吨、× 驱动）单独抽成结构化槽。search_key = 归一化品牌片段 + 结构化槽。
- 为什么先试：直接产出任务要的 key；不需要标注；失败可解释；产出的「闭类词表」是数据自举的，不违反「不维护品牌词表」。
- 验收：抽 100 条，人工看 key 是否稳定；同款不同写法的 key 碰撞率；跨品牌误合并率。

**B. 手写 Fellegi–Sunter 加权打分（不必上 Splink）+ 三档阈值**
- 做法：把 A 产出的槽位当字段，每字段给「完全匹配 / 部分匹配 / 冲突」三档权重（数字槽冲突直接判负），加权求和；`-1/0/+1` 三档阈值分流到「自动合并 / 人工队列 / 自动拒绝」。
- 为什么先试：本质是 Splink 的思想但只有一个公式，可调试；先手写把权重跑明白，再决定要不要换成 Splink 的 EM 自动估参。
- 验收：灰区占比（目标 <10%）、人工队列的精确率、以及「375 马力 vs 380 马力」这类只差数字的负例是否被正确拒绝。

**再往后**：A+B 跑通、有了几百条人工判定后，再考虑 (4) SC-Block 做候选合并、(6) LLM 只啃灰区。顺序不要反——先有可解释 baseline，再加模型。
