## 先建立一个判断：搜索式AI产品不是“更好的搜索引擎”，而是“把搜索从终点变成起点”

传统搜索的产品逻辑是：用户输入关键词 → 返回链接列表 → 用户自己点击、浏览、判断、综合。搜索是**终点**。

搜索式AI产品（Perplexity、Perplexica、各类“答案引擎”）的逻辑是：用户提出一个问题 → 系统**主动获取、筛选、综合**信息 → 直接交付一个带引用的答案或可执行结果。搜索变成了**中间环节**。

这个变化带来的直接后果是：**信息质量的责任从用户转移到了产品身上**。传统搜索里，结果里有垃圾内容，用户自己会跳过；搜索式AI产品如果索引了垃圾、过时或不相关的内容，它会**自信地输出一个错误答案**。所以整条技术栈的重心，从“如何返回更多结果”，变成了“如何确保进入生成环节的内容是干净的、相关的、足够的”。

下面按用户提到的几个问题，逐层拆解。


## 一、内容获取与反爬：产品要的不是“爬虫”，是“稳定、合法、可规模化地拿到干净内容”

### 产品要解决的问题
搜索式AI产品需要实时或近实时地触达公开网络。但目标网页越来越不友好：大量站点是JavaScript渲染的单页应用，直接抓HTML只能拿到一个空壳；Cloudflare、DataDome等反爬服务会拦截自动化请求；即使请求成功，返回的原始HTML里80%以上是导航、广告、脚本和样式，真正的内容可能只占很小比例。

**对产品而言，这不是“技术实现”问题，而是“数据供给的可靠性”问题**：反爬失败一次，索引里就可能缺一块；空壳页面被当作真实内容入库，答案就会基于空气生成。有从业者的总结很直白：一个被封锁的抓取会在索引里留下空洞，而LLM会对着空洞产生幻觉。

### 技术栈上的典型解法
行业里正在把“网页内容获取”**从每个团队自己维护爬虫，变成调用专门的“为AI准备的获取层”**。典型产品/开源项目：

- **Firecrawl**：API-first的网页抓取与转换引擎，核心卖点是处理JavaScript渲染、反爬绕过和DOM清洗，直接输出**LLM就绪的Markdown**。它内部用Playwright无头浏览器池、代理轮换和DOM净化器来应对动态页面和Cloudflare类防护。GitHub上开源，同时有云服务。
- **Tavily**：定位更靠前，是“为Agent和RAG应用设计的搜索与提取引擎”，直接提供 `tavily_search` 类接口，内部处理反爬、JS渲染和token优化，返回结构化、去重的摘要和URL。
- **Searqon**：开源的轻量替代品，用Go编写，实现了**四层递进式反爬**：从快速HTTP请求，到浏览器TLS指纹伪造（模拟Chrome/Safari/Edge），再到无头浏览器执行，最后回退到住宅代理，专门用来穿透Cloudflare Turnstile、DataDome等挑战。
- **SearXNG**：开源的元搜索引擎，本身不爬全网，而是聚合70+搜索源的结果，常作为Perplexica等产品的“搜索层”。

### 产品视角的取舍
自建爬虫vs调用获取层，是一个典型的**成本与可靠性权衡**。自建意味着控制力强，但要持续维护浏览器池、代理网络和反爬对抗，是持续的工程负担；调用Firecrawl/Tavily类服务把这块“外包”，换取的是开箱即用的反爬和格式标准化，代价是API成本和对第三方的依赖。Searqon这类开源方案提供了一个中间选项：可以自托管、可控成本，但需要自己运维。


## 二、清洗与识别：垃圾进，不一定是垃圾出——而是“浪费的Token + 被污染的向量空间”

### 产品要解决的问题
从网页拿到原始HTML，到能送进模型或索引，中间有一个容易被低估的环节：**清洗**。原始HTML里大部分内容对回答问题是噪音。如果不清洗，后果不只是“答案质量差一点”，而是：

1. **Token浪费**：把导航、广告、脚本塞进上下文窗口，直接推高每次生成的成本，而且会把真正有用的内容“挤出去”。
2. **向量污染**：如果把带噪音的整页内容做成embedding，检索时会召回到大量“看似相关、实则无用”的片段。
3. **安全与合规风险**：低质、操纵性或对抗性内容混入，可能诱导模型输出偏差或有害内容。

有RAG工程文章把这一点总结为：**RAG的质量等于语料的质量，检索答案的上限由你索引的文本决定**；而大多数管道失败，追溯回去都是“页面从未真正渲染”、“导航框架被嵌入”、“chunk在句子中途被切断”。

### 技术栈上的典型解法
清洗层通常包含几个动作：**正文提取**（把导航、页脚、广告、cookie横幅剥掉）、**格式转换**（HTML → 干净Markdown）、**分块**（把长文档切成语义完整的片段）、以及**质量门控**（判断这一页是否值得入库）。

- Firecrawl和Tavily的“DOM sanitizer / HTML-to-Markdown transformer”本质上就是在做**减法**：把复杂DOM结构翻译成token优化的纯文本，只保留可被模型消费的内容。
- 更上游还有**内容质量识别**的问题。当前一个真实的产品痛点是“AI Slop”（AI生成的低质填充内容）正在污染搜索结果，这类内容“看起来有内容，实际上没有”，检测它需要超越关键词匹配，从结构性、重复性、空洞性等维度判断。已经有Pangram、ClearWater等产品在专门解决这个问题。
- 在生产级RAG管道中，一个被强调的设计原则是：**把“被阻止的页面”和“空页面”当作一等公民结果来处理**，而不是当作异常忽略。也就是说，如果抓取失败或拿到空壳，宁可不更新索引，也不能让坏数据替换好数据。

### 产品视角的取舍
清洗层的产品决策核心是：**“多干净”和“保留多少上下文”之间的平衡**。过度清洗可能丢掉有用信息（比如表格结构、代码块），清洗不足则引入噪音。分块策略同理：切得太碎丢失上下文，切得太大引入噪音并降低检索精度。这不是一个纯技术参数问题，而是**产品对“什么样的内容形态最能支撑高质量回答”的判断**。


## 三、召回与排序：搜索式AI的“检索”不是关键词匹配，而是“在正确的候选集里找正确的片段”

### 产品要解决的问题
传统搜索的召回是“文档级”的：找出包含关键词的网页，按链接权重排序。搜索式AI产品需要的是**片段级**的精准召回：在生成答案之前，只把少量真正相关的文本片段送进上下文窗口。如果召回不准，后面用再强的模型也救不回来。有工程实践中的经验判断是：在检索-排序类AI场景中，**检索质量的80%由排序算法决定，模型最终优化只占约20%**。

### 技术栈上的典型解法：从“级联漏斗”到“混合检索 + 重排”

传统搜索和推荐系统共用一套成熟的漏斗架构：**召回 → 粗排 → 精排 → 重排**。召回从海量候选（百万到千万级）中快速筛出几千个可能相关的；粗排用轻量模型（LR、GBDT、LightGBM）快速淘汰大部分；精排用复杂模型做精细打分；重排处理多样性和业务规则。

搜索式AI产品继承了这个骨架，但在每个环节上做了AI化改造：

- **混合召回**：不再只依赖关键词，而是同时使用**稀疏检索**（BM25/全文索引，擅长精确匹配和实体匹配）和**稠密检索**（向量Embedding，擅长语义扩展和意图理解）。阿里云的AI Search架构明确采用这种“稀疏+稠密”混合路线。
- **重排是产品差异化的关键**：向量召回负责“宽”，重排模型（Reranker）负责“准”。一个典型的Agentic RAG实现会包含多路检索（向量+BM25+知识图谱+网络搜索），然后经过**相关性检查**和**Self-RAG质量评估**，形成闭环纠错。Firecrawl/Tavily输出的“precision relevance scores”本质上就是重排信号。
- **Agentic Search的进一步演化**：阿里云的Agentic Search把搜索、推理、规划和工具调用融合成一个闭环，模型不只是“检索一次然后回答”，而是可以**多步检索、查询重写、交叉验证**，甚至调用外部工具。这意味着召回不再是一次静态操作，而是由Agent根据中间结果动态决定“下一步该查什么”。

### 产品视角的取舍
召回与排序层的核心产品决策是：**精度与召回率的权衡，以及延迟与成本的权衡**。混合检索和重排能显著提升答案质量，但会增加检索延迟和算力成本。Agentic的多步检索进一步放大了这种权衡：多检索几步可能找到更好的证据，但用户等不起，成本也扛不住。所以很多产品会在“快速路径”（一次检索直接回答）和“深度路径”（多步研究）之间做产品分层。


## 四、一个容易被忽视的产品层：查询理解与任务编排

用户提到的“有效信息淹没”，很多时候不是检索层的问题，而是**查询理解和任务编排**的问题。用户问“帮我找一下适合小团队的CRM工具，最好支持自动化”，如果系统直接拿整句话去做关键词检索，召回质量注定有限。产品化的做法是：先把查询拆解为**意图、约束、子任务**，再分别决定用什么检索策略、调什么工具、生成什么中间查询。

开源的**Agentic RAG**项目提供了可参考的编排模式。比如 `xingzhangg/ragent` 覆盖了文档解析、多路检索、意图识别、问题重写、会话记忆和MCP工具调用；`dyj-naj/Agentic-RAG-Knowledge-Assistant` 的核心是一条7阶段流水线：查询优化 → 意图识别 → 任务拆解 → ReAct代理检索 → 相关性检查 → 答案生成 → Self-RAG质量评估。这些项目反映的产品思路是：**搜索式AI的质量，很大程度上由“检索之前和检索之间的决策”决定**，而不是单靠模型能力。

## 最后：用产品语言总结这套技术栈到底在解决什么

搜索式AI产品技术栈的底层逻辑，可以压缩成一句话：**在“内容从公开网络到达用户答案”的每一个环节，把“不可靠”变成“可控”**。

- **获取层**解决的是“**能不能稳定拿到干净内容**”——反爬和JS渲染是手段，可靠性是目的。
- **清洗层**解决的是“**进入生成环节的东西值不值得被消费**”——去噪和分块是手段，Token效率和索引质量是目的。
- **召回排序层**解决的是“**在正确的位置找到正确的片段**”——混合检索和重排是手段，答案的grounding是目的。
- **编排层**解决的是“**复杂问题需要拆成什么样的检索和推理步骤**”——Agent和多步检索是手段，复杂任务的可完成性是目的。

对产品经理而言，最关键的判断不是“选哪个模型”或“用不用向量数据库”，而是：**你的产品在哪个环节最脆弱，就在哪个环节优先投入**。如果目标是做一个快速的答案引擎，获取层和重排层是杠杆最大的；如果要做深度研究型产品，编排层和Self-RAG的质量闭环才是差异化所在。


**一个建议性的下一步**：如果想用最小成本建立体感，可以先用 **Perplexica + SearXNG + Ollama** 跑一个自托管的搜索式AI原型（Docker Compose即可），然后尝试把其中的获取层替换为 **Firecrawl** 或 **Searqon**，对比“原始HTML vs 清洗后Markdown”对答案质量和Token消耗的影响。这个对比会让你对上述每一层“到底值多少钱”形成直接的体感。

# 问：
好，现在我需要你帮我分析一下我的项目，我做了一个用于分析工程车辆外观部件的产品，包含检索与分析模块，现在分析模块在多模特模型与少量引导的情况下已经能对于图片上的工程车外观部件进行有效准确合规的结构化分析。现在问题出在检索模块，传统方式是人在ai平台询问某种类型的一系列车的型号和简要介绍和官网链接（当然还缺少核验），然后由人去官网找图片（找不到就其它平台搜图）然后下载下来再进入分析模块，这些步骤非常耗时，所以我想要用ai agent或者workflow来提效和校验，需要ai来推荐要分析的车名单和提供相关图片，那么问题来了：以用户输入沙漠牵引车并分析保险杠、防护栏、前脸、轮拱、蹬车踏步为例，用户可能想看沙漠环境下的某些部件的环境特化设计，可能想看看同基础构型（沙漠牵引车本质看着像普通卡车头，只是底盘高、部件有特殊设计比如大车灯有金属丝网罩）的前脸怎么设计的，所以哪些需要找沙漠牵引车来分析，哪些只需要找普通卡车来分析就足够了（比如前脸的设计并不与沙漠环境强相关，可以找一些好看的卡车进行参考），由于我们不可能穷举完用户要分析哪些类型的工程车辆和部件，所以需要设计这个分析并推荐的架构，这是否属于检索前的策略设计？还要考虑到这种专业的一本正经的外观分析非常少，网上多是宣传广告等等宣发内容，并且还有获取图片这一任务，图与型号对应又是个问题，所以需要你帮我看看怎么设计检索前检索中和检索后的策略，是不是先按某种方式分析用户输入的车辆和部件（比如通过设计一个skill来进行标准的分析）来决定要检索的方向（比如找沙漠牵引车和沙漠卡车来分析登车踏步等等部件在沙漠环境下的设计和车辆整体姿态比如底盘高度，找普通卡车来进行前脸参考，找任意带防护栏的卡车来进行检索来作为防护栏的造型参考），然后才是具体去找内容么，是找通过文本找还是通过图来找，有效信息一定是淹没在大量不需要的信息中的，需要什么样的文本来确认一些什么样的信息，你结合以上内容系统地考虑一下，可能我的一些流程不是合适的，你要指出并给出推荐

# 答：
你的直觉是对的：**“先分析用户输入，再决定检索方向”这一步，确实属于检索前的策略设计**。但它不应该被设计成一个笼统的“skill”，而应该拆成两层：**部件-环境相关性分类器**（决定“要不要找沙漠车”）和**检索策略路由器**（决定“用什么方式找、找什么形态的证据”）。在Agentic RAG的成熟架构里，这正是Query Planning Agent在做的事：先对查询做结构化拆解，再把子任务分派给专精于不同检索路径的Agent。

但在展开架构之前，你的流程里有一个**更关键的不合适之处**需要先指出：你把“推荐车型名单”和“获取图片”当成了一个线性步骤。这会导致检索目标漂移——Agent可能会先找到一堆“沙漠牵引车”的型号，然后被迫去为这些型号找图，哪怕这些图根本不适合分析你关心的部件。正确的逻辑应该反过来：**先定义“对这个部件来说，什么才算有效视觉证据”，再倒推需要什么类型的车、以及去哪里找这种图片**。


## 检索前：核心不是“推荐车名单”，是“判断每个部件的设计约束是否与环境强相关”

你举的沙漠牵引车例子，恰好暴露了问题的本质。用户说“分析保险杠、防护栏、前脸、轮拱、蹬车踏步”，但这五个部件对“沙漠环境”这个属性的敏感度是完全不同的：

- **保险杠、防护栏、蹬车踏步**：沙漠环境可能带来特定的防护需求（沙石冲击、防滑、耐高温），这些部件的设计**可能与沙漠强相关**，值得优先检索沙漠工况车辆。
- **前脸**：前脸的造型语言、灯组布局、格栅比例，**与沙漠环境几乎没有因果关系**。找沙漠牵引车来分析前脸，是在用“环境标签”掩盖“设计参考”的真实需求。
- **轮拱**：介于两者之间，沙漠可能影响离地间隙和轮拱开口形态，但轮拱本身的造型选择有大量非环境驱动的设计自由度。

所以检索前策略的第一个动作，不是“推荐车型”，而是**对用户输入的每一个“车辆类型 × 部件”组合，独立打一个“环境相关性标签”**。这个标签可以是一个简单的三值判断：

| 相关性 | 含义 | 检索目标 |
|---|---|---|
| **强相关** | 该部件的功能/形态受环境约束显著 | 必须找到**沙漠工况下实际使用的该部件**作为证据 |
| **弱相关** | 环境可能有影响，但设计自由度大 | 沙漠车和普通车都收，以“设计质量”为筛选标准 |
| **不相关** | 该部件的设计逻辑与环境无关 | **忽略“沙漠”这个修饰词**，在全量高质量卡车中检索 |

这个分类器不需要穷举。你可以把它做成一个**可配置的部件-属性关联矩阵**，初始覆盖你已知的部件类别，遇到新部件时由LLM基于“该部件的核心功能是什么、环境通过什么机制影响这个功能”做零样本推断，人工复核后沉淀进矩阵。StrategyLibrary的思路正是如此：将查询匹配到预定义的策略模板，而不是每次让LLM从零推理。

**需要修正的第二点**：你在问题里说“找普通卡车来进行前脸参考”——这个表述需要收紧。“普通卡车”的检索边界太宽，会把大量广告图、无关车型卷进来。检索前策略应该把“参考”进一步定义为**“有明确设计意图的、可归因到具体车型的前脸视觉证据”**，而不是泛泛的“好看的卡车图片”。这意味着检索目标从“卡车”收窄到“已知型号的、有官方或高质量实拍图的卡车”。


## 检索中：文本和图像不是二选一，而是两条并行通道，且“先文后图”和“先图后文”适用于不同任务

你问“通过文本找还是通过图来找”，答案取决于检索前的分类结果：

**通道A：先文后图（文本寻址 → 图片定位）**  
适用于**强相关/弱相关**的部件。先用文本确认“沙漠工况下保险杠/防护栏存在哪些已知的设计变体”，再从这些变体对应的车型或配置去定位图片。文本在这里的作用是**建立检索的语义锚点**，防止图片检索被“看起来像沙漠”的视觉噪声带偏。例如，沙漠车常见的保险杠防护结构可能有“管状防撞杠”“分段式沙石挡板”等具体形态，这些概念应该先从文本中获取，再用它们去约束图片检索。

**通道B：先图后文（图像寻址 → 型号/部件确认）**  
适用于**不相关**的部件（如前脸），或者用户已经提供了参考图的情况。直接用“沙漠牵引车前脸”“越野卡车前脸”等图像查询做视觉检索，找到候选图后，再用视觉模型或文本信息反向确认这张图对应什么型号、什么部件。但这条通道有一个必须警惕的陷阱：**标准的以图搜图在部件级别会产生大量“视觉泛化噪声”**——所有“看起来差不多”的卡车前脸都会被召回，但其中大部分在具体设计上并不具有参考价值。BrumBuster的实践者明确记录了这个问题：标准视觉搜索会把所有发亮的刹车盘或银色轮毂当成“相同”的，产生海量误报。

因此，**检索中的核心产品决策是：对“不相关”部件，不以视觉相似度为唯一排序信号，而是引入“设计归因质量”作为重排维度**。一张来自已知车型、有明确品牌/型号上下文的前脸图，其参考价值远高于一张无法归因的“好看卡车图”。这就需要检索中同时维护**图片和其来源页面的型号元数据**，而不是把图片从上下文中剥离出来单独入库。

**关于反爬和清洗**，在你的场景里有一个被低估的现实：工程机械官网恰恰是**结构化数据最贫瘠的地方之一**。行业观察指出，大量工程机械企业官网的产品参数“全是图片”、菜单靠脚本拼接、正文滚动加载，抓取程序读不到有效文本。这意味着你不能假设“官网产品页 = 可靠的图文对应来源”。检索中应该把来源分层：

- **优先层**：有JSON-LD结构化标记的页面（部分国际品牌如Volvo CE做得较好），可以直接从结构化数据中提取型号、图片和参数。
- **次级层**：需要无头浏览器渲染、但页面结构相对规整的经销商或行业垂直站点。
- **兜底层**：**外观设计专利数据库**。这是一个你目前流程中完全缺失、但对“部件级造型参考”极其匹配的来源。国家知识产权局的外观设计专利检索系统支持图像检索和混合检索，覆盖多国数据库，专利图片是**去语境化的、聚焦造型的、且附带型号/申请人元数据**的高质量视觉证据。对于“前脸造型参考”这类需求，外观专利图可能比官网宣传图更干净、更可归因。


## 检索后：不能只做“图文相关性判断”，要做“三证核验”

你提到“图与型号对应是个问题”，这触及了检索后环节的真正难点。单一的“这张图和这个型号匹配吗”判断是不够的，因为即使匹配了型号，图片里的部件也不一定是你要分析的那个；即使部件对了，图片的拍摄状态（角度、光照、是否改装）也可能让它在你的分析模块里不可用。

检索后应该建立**三证核验**：

**第一证：型号-图片归属。** 这张图是否确实对应所声称的型号。核验手段包括：图片所在页面的标题/结构化数据中的型号字段、图片URL或文件名中的型号线索、以及用视觉模型比对已知该型号的特征（大灯轮廓、格栅形状等）。Pailitao-VL的研究指出，即使区分轿车和SUV这类粗粒度任务可行，识别“小改款车型的细微大灯轮廓差异”仍然是难点，所以这一步不能只靠通用视觉相似度，需要**把你在分析模块中已经积累的部件级结构知识反哺到核验环节**。

**第二证：部件-图片可见性。** 这张图是否以足够的分辨率和角度展示了目标部件。一张沙漠牵引车的远景图，可能“证明”了底盘高度，但对保险杠的细节分析毫无用处。检索后需要输出一个**部件可见性标签**（清晰可见/部分可见/不可见），并据此决定是否将这张图送入分析模块。

**第三证：改装/原厂状态。** 图片中的部件是原厂配置还是后市场改装。对“设计参考”而言，改装件和原厂件的证据价值不同，尤其是在“防护栏”“保险杠”这类高改装率部件上。BrumBuster的教训值得直接借鉴：它专门设计了逻辑来检测库存图和实际零件的差异，以避免“一张 glossy stock cover photo”掩盖真实的部件状态。你的场景不需要做到法证级，但至少应该把“无法确认是否原厂”的图片降权或单独标记。

三证核验的输出，不应该是一个二值的“通过/不通过”，而应该是**一个带置信度和缺陷标签的证据记录**。这样你的分析模块在收到图片时，已经知道“这张图对保险杠分析的证据强度是中等，因为角度偏侧且无法确认是否改装”，而不是拿到一张图却不知道它在哪个维度上不可靠。


## 对你流程的总结性修正，以及一个可落地的架构建议

你的原始流程大致是：**用户输入 → 推荐车型名单 → 找官网/搜图 → 下载 → 分析**。建议调整为：

**用户输入 → 部件-环境相关性分类（检索前）→ 分通道检索与来源分层（检索中）→ 三证核验与证据标注（检索后）→ 分析模块**

其中，检索前分类器的输出不是一个“车型名单”，而是**一组“检索任务单”**，每个任务单包含：目标部件、相关性标签、检索通道（先文后图/先图后文）、来源优先级、以及“什么算有效证据”的验收条件。检索中Agent按照任务单执行，而不是自由发挥去“推荐车”。

**一个被忽视但杠杆很高的设计**：不要每次从全网重新检索。你的场景天然适合建立一个**部件-环境证据库**，把三证核验通过的高质量图文对沉淀下来。当用户再次输入“沙漠牵引车 + 保险杠”时，系统优先从证据库中召回已经核验过的记录，只对覆盖不足的部分触发外部检索。这既降低了反爬压力和API成本，也让检索质量随着使用逐步提升——本质上是在用检索后的核验结果，反向优化检索前的策略库。


**还有一个需要你重新审视的假设**：你说“分析模块在多模态模型与少量引导下已经能对图片进行有效准确合规的结构化分析”。如果这个判断是可靠的，那么检索模块的验收标准就不应该是“找到足够多的图片”，而应该是**“找到的图片能让分析模块产出高置信度的结构化结论”**。这意味着检索后核验环节可以直接调用分析模块作为**证据质量裁判**：一张图片送入分析模块后，如果输出的结构化字段大量缺失或置信度低，这张图片就应该被标记为“证据不足”，而不是被当作有效输入。把这个信号回流到检索策略中，就形成了一个**以分析可用性为终点的检索闭环**，而不是一个以“找到图片”为终点的开放检索。

## 先说框架：为什么是 LangGraph，而不是“LangChain”

LangChain 和 LangGraph 是同一个生态里的两层东西：LangChain 提供模型接入、文档加载、向量库连接这些“零件”，LangGraph 负责“把这些零件按什么顺序、什么条件串起来”。你真正需要的是后者。

LangGraph 的核心抽象是**状态图**：节点是处理步骤，边是条件路由，整个图共享一个可检查点的状态对象。这恰好对应你上一轮描述的检索流程——检索前分类产出“任务单”写入状态，检索中 Agent 按任务单执行并把证据记录回写状态，检索后核验读取状态做判断，再决定是否触发补充检索。这种**“根据中间结果决定下一步走哪条分支”**的逻辑，用 LangGraph 的条件边表达是自然的；用 LangChain 的线性 chain 表达则会很别扭。

一个更实际的理由来自成本。多 Agent 编排的框架选择直接影响 token 消耗，LangGraph 在复杂任务中的 token 效率是几个主流框架里最高的，而 AutoGen 在同类任务上的消耗可以达到 LangGraph 的数倍。你的检索流程涉及多轮、多通道的决策，如果框架本身在每次循环里都产生冗余推理，成本会迅速失控。

**CrewAI 为什么不合适**：CrewAI 的隐喻是“角色团队”，适合内容管线或研究任务那种“几个角色各干各的、最后汇总”的场景。你的检索流程有严格的顺序依赖和条件分支（分类 → 分通道检索 → 核验 → 补充检索），不是平行角色协作，硬套 CrewAI 会让流程变得不自然。

**AutoGen 为什么不合适**：AutoGen 已经进入维护模式，且对话式协调在你的场景里会引入不必要的不可控性。你不需要“Agent 之间自由对话”，你需要的是“在关键判断点让模型做一次受限决策”。

**LangChain 还要不要用**：用，但只作为“零件库”。LangChain 的文档加载器、向量库接口和工具封装可以继续用，但编排层交给 LangGraph。这不是二选一，是分工。


## 编排模式：Workflow 为骨，Agent 为肉，只在两个节点放手

搜索材料里反复出现的共识是：**能确定的用 Workflow，该动态的用 Agent，混搭是 2026 年生产级方案的主流形态**。你的流程里，绝大部分步骤是确定性的：

- 用户输入进来后，**部件-环境相关性分类**需要判断，但判断完之后走哪条通道是规则决定的；
- 文本检索和图片检索的**执行顺序和工具调用是确定的**；
- 三证核验的**检查项是预先定义好的**；
- 证据入库和降权标记的**逻辑也是确定的**。

真正需要 Agent 动态决策的，只有两处：

**第一处：检索前的部件-环境相关性判断。** 这不是一个可以用关键词规则覆盖的任务，需要模型理解“这个部件的核心功能是什么、环境通过什么机制影响这个功能”。但它应该被约束为一个**单步结构化输出任务**——给定部件名称和车辆类型，输出强相关/弱相关/不相关以及理由，而不是让 Agent 自由规划后续所有检索步骤。用 LangGraph 表达就是：一个节点调用模型做分类，一个条件边根据分类结果路由到不同的检索子图。

**第二处：检索后的“证据质量裁判”。** 你上一轮提到可以用分析模块反向判断图片是否“可用”。这个判断本身也是模型驱动的，适合放在一个 Agent 节点里：读取三证核验的中间结果和分析模块返回的结构化字段完整度，输出“通过 / 降权 / 退回补充检索”。退回时，LangGraph 的条件边可以把流程送回检索中节点，形成一个有界的纠错闭环。

**一个容易被忽略的架构原则**：Agent 的自主权应该被“预算”约束。检索后裁判可以决定“再搜一次”，但不能无限循环。LangGraph 的检查点和状态机制天然支持在状态里记录循环次数，达到上限就强制进入人工复核或降级输出。这是纯 Agent 框架很难干净实现的。


## 部署平台：分两阶段，前期别在基础设施上耗时间

你是一个产品驱动、不是工程团队驱动的项目，部署策略应该和你的阶段匹配。

**第一阶段（验证流程假设）：用 Dify 或 n8n 搭前端骨架。** Dify 的开源版本可以自托管，可视化编排对产品经理友好，适合先跑通“用户输入 → 任务单生成 → 检索执行 → 结果展示”的完整体验。n8n 的优势在于节点生态更偏“自动化连接”，如果你的检索需要频繁对接外部 API（爬虫服务、专利数据库、云存储），n8n 的 HTTP 节点和条件分支比 Dify 更顺手。这一阶段的目标不是上线，是**让业务流程在真实数据上跑起来，确认哪些判断规则需要调整**。

**第二阶段（核心编排落到 LangGraph，私有化部署）。** 当流程假设基本稳定、需要做“有界纠错闭环”和“分析模块反向裁判”时，Dify 或 n8n 的表达能力会开始吃力。这时候把 LangGraph 作为编排内核引入。部署形态上，LangGraph 是开源库，本身不绑定云平台，可以自托管在私有服务器上。考虑到你的产品涉及爬虫获取第三方内容和调用内部署的分析模块，**数据不出私有环境是合理底线**——Coze 这类纯 SaaS 平台在这一点上直接排除。

**向量存储和图片检索的选型**：你的场景是图文混合检索，Milvus 是当前最成熟的选择，支持多模态 embedding 的联合检索，并且有成熟的自托管方案。如果团队规模小、不想维护独立向量数据库，Qdrant 的轻量部署也是合理选项。但有一点需要提前想清楚：**你的图片检索不应该是纯视觉相似度**，而应该是“视觉召回 + 型号/来源元数据过滤 + 多模态重排”的三层结构。重排层可以用一个多模态模型对候选图片做最终判断，这正是你“三证核验”的落地位置。


## 一个建议性的落地顺序

不要从“搭完整架构”开始。按这个顺序，每一步都产出可验证的东西：

**第一步：把“任务单”数据结构定下来。** 这是整个系统的契约。检索前分类的输出、检索中每个通道的执行记录、检索后三证核验的标签，都挂在同一个任务单对象上。先用伪代码或表格定义清楚，再选框架。

**第二步：用 Dify 或 n8n 跑通“单任务单、单通道”的最小闭环。** 选一个你熟悉的部件（比如保险杠）和一个通道（先文后图），把分类、检索、核验、入库串起来，手动注入几张图片看分析模块的反向信号是否可用。**这一步的目的是验证“证据质量裁判”这个假设是否成立**，而不是验证框架。

**第三步：确认假设后，迁移到 LangGraph，只迁移需要动态决策的部分。** 固定的步骤可以用普通函数写，只有分类节点和裁判节点用模型。LangGraph 的图中可以有“非 Agent 节点”，这是它的灵活性所在，也是控制成本的手段。

**第四步：再考虑多通道并行和证据库沉淀。** 当单通道闭环稳定后，图片检索通道和专利数据库通道才值得加入。证据库（已核验的图文对）的优先级应该高于扩展新通道——它直接降低后续检索的爬虫压力，是复利最高的投入。


**最后需要你提前想清楚的一个产品决策**：检索后裁判调用分析模块做反向验证，意味着**分析模块会被检索流程高频调用**。如果分析模块的延迟或成本不适合这种用法，三证核验的第三证（证据可用性）可能需要降级为“抽样裁判”而不是“全量裁判”。这个取舍应该在架构设计阶段就暴露出来，而不是等系统跑起来才发现检索被分析模块的瓶颈卡住。
