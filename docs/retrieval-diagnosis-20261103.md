## 1. 图片检索现在实际怎么走

一次"某车型取主图"的完整链路（`web/server.py::_harvest` → `imagesearch.py` → `gate.py`）：

```
查询阶梯      "{型号} 工程车" → "{型号}"（两段，去重合并）
   ↓
通道         360图片 → 百度图片 → Bing图片（逐通道累加，够数即停）
   ↓
相关性护栏   仅看标题文案：非车词一票否决 / 构型词必须一致 / 型号代码或品牌+车辆词命中
   ↓
下载         6 线程并行，8MB 上限，宽度 ≥350px
   ↓
门卫(CLIP)   keep/drop 标签集竞争，margin>0 放行；再判视角 front/rear/hero_45/side/interior/detail
   ↓
类别门卫     乘用车/SUV/皮卡 丢弃；图题型号冲突 丢弃
   ↓
入库         binding_evidence = co_occurrence_only（T3 弱关联，等人工确认）
```

**真实产出（最近一次 harvest，`data/web-runs/harvest-7b722b5a/result.json`）**

| 车型 | 360 | 百度 | Bing | 最终入库 |
|---|---|---|---|---|
| 德龙6X6（查询"德龙6X6 工程车"） | 12 条 → 相关 **2** | 0（empty） | 12 条 → 相关 **0** | — |
| 德龙6X6（查询"德龙6X6"） | 12 条 → 相关 **10** | 未请求（已够数） | 未请求 | — |

6 台候选共 18 张入库、8 张被门卫拦（`gated_out`）。结论：**360 一条腿在扛，百度和 Bing 实际上是死的**。

## 2. 短板排序（按对结果质量的影响）

### ① 通道单点，且没有"换路"能力（最硬）
360 → 百度 → Bing 是"并列尝试"，不是"降级"。没有：出口 IP 轮换、失败退避、按通道健康度熔断、结果缓存（同一查询重复跑仍重新请求）。
百度返回 `antiFlag: Forbid spider access` 或安全验证页，Bing 中文图返回壁纸/人物（实测相关 0/12），两者都被当作"尝试过了"。

### ② 相关性判断只发生在标题文本上
`_relevant()` 是关键词规则。同一个车型，加一个"工程车"后缀，相关率从 10/12 掉到 2/12——说明护栏对标题措辞极度敏感，且**没有任何图像级信号参与召回**。
后果：要么漏（好图被标题规则毙掉），要么错（标题对、图不对）。

### ③ 门卫只回答"是不是一台工程车"，不回答"是不是这台车"
CLIP 零样本门卫（`gate.py`，22ms/图，30 样本人工校准 93% 一致）解决的是**杂质**，不是**身份**。
- 型号身份目前依赖：标题含型号代码 + 构型词一致 + 人工复核；
- T14 的四组构型混杂（STC800C6 / XCT8L4 / QY16KC / QY25K5C）证明：同一型号名可覆盖多构型/改款，机器判不了；
- T13 的 J6G 组 5 张错配同理；
- 这就是你说的"图片匹配功能不够强"的真正位置——**不是召回不够，是校验不够**。

### ④ 已有的图片匹配能力（盘点，避免重复造）
| 能力 | 位置 | 强度 |
|---|---|---|
| dHash 近重复去重（16 位，汉明距离） | `ingest.dhash` / `query.py` | 可用，只能抓"几乎同一张" |
| CLIP 零样本杂质门卫 + 场景分类 | `gate.py` | 可用，93% 一致（30 样本） |
| CLIP 视角分类（含左右不定态） | `gate.py` / `probe.py` | 可用但天花板明确：左右分不清，长尾车型泛化差 |
| 类别门卫（卡车 vs 乘用车/SUV） | `gate.classify_labels` | 可用 |
| 区域匹配 `region_match`（T1 强证据） | 仅 schema 枚举，**未实装** | 缺口 |
| 反向搜图（Google Lens / Bing Visual） | 无 | 缺口 |
| 与参考图"同款比对" | 无 | 缺口 |

### ⑤ 降级/兜底链的实际情况（文字检索侧）
`runner.py`：auto → 延迟 4s 重试 → Bing。Bing 兜底实测不可用（RSS 拆词、HTML 无有效锚点），所以等价于**单通道 + 一次重试**。
`strategy.py` 的 replan/stop 是**指标级**兜底（文章数/A 档占比不足就重规划或停下问人），解决"要不要继续"，不解决"换哪条路"。

## 3. 爬取检索的主要阻碍（分四层，各带证据）

| 层 | 阻碍 | 证据 | 含义 |
|---|---|---|---|
| 网络/反爬 | 百度网页搜索直连必触发验证；图片 API 返回 `antiFlag: Forbid spider access` | HANDOFF §204、T18-budget-curve（4 档预算全部 SERP 6/6 blocked、0 篇） | 不是"慢慢抓就行"，是**入口被判死** |
| 通道 | 图片搜索只剩 360 可用；Bing 中文图相关率 0 | 上文 harvest 诊断表 | 单点故障 |
| 合规 | robots 拒绝；百度跳转链接导致 17/17 全拒（已修：先解析真实 URL） | T16 | 合规成本真实存在，但不是主因 |
| 语义 | 类目词与市场用词不一致（翻斗铲车≈自卸车）；同名多构型；图题与图不符 | T15 意见 #17、T14 意见 #16、T13 | 决定"抓回来的是不是对的东西"，与反爬无关 |

**归因**：我们已经在用真浏览器（Crawl4AI/Playwright）渲染百度 SERP，仍然被拦。说明阻碍主要来自**出口 IP + 请求模式 + 无登录态**，而不是"浏览器不够像人"。

## 4. computer use 能不能解决反爬

机制对比：

| 维度 | Playwright / CDP | computer use（截图 + 系统级鼠标键盘） |
|---|---|---|
| JS 指纹（`navigator.webdriver`、CDP 注入痕迹） | 暴露，需 patch | 天然不暴露（驱动的是普通浏览器） |
| 行为轨迹（鼠标曲线、节奏） | 合成事件，易被识别 | 接近真人 |
| TLS/HTTP2 指纹 | 取决于浏览器 | 同左（同一浏览器） |
| 出口 IP / ASN 信誉 | 不改变 | **不改变** |
| 验证码 / Turnstile | 拦 | 拦，只能靠 VLM 看图点选 |
| 速度 | 百毫秒级 | 秒级（截图-推理-动作） |
| 成本 | 近乎零 | 每步一次多模态调用 |
| 稳定性 | 高（可重放） | 低（视觉误差累积） |

**判断**：computer use 主要补的是"指纹与行为"这两格；它**不动 IP 与验证码**，而这两条正是我们当前的实际拦截原因（真浏览器同样被拦）。再加上速度慢两个数量级、不可重放（与本产品"可复现/账本"的核心价值冲突），**现在换过去不划算**。

真正能提升通过率的三件事，按性价比：
1. **换出口**：住宅/移动代理池，或按域名限速 + 错峰（成本最低、见效最快）；
2. **少抓**：官方 API / 付费 SERP API（如 Bing Search API、Serper）/ 厂商开放数据，把"抓"降级为"取"；
3. **人在环**：验证码出现即转人工确认（一次点击），而不是让机器硬闯。

computer use 值得保留的位置：**只在"必须登录/必须点选"的关键页面**做少量兜底，不做全链路主力。

## 5. 做成 DSH 插件（侧边栏）是否更有优势

### 技术事实（已在安装包内核实）
DeepSeek Harness 是 Cordis 插件体系，插件分三类：
- **Host 插件**：在宿主进程内跑 Node 代码（可起服务、可读写文件、可注册工具）；
- **Client UI 插件**：注册界面席位。右侧栏提供公开的 tab 类型注册表 `ctx.sidebarRightTabs.register({id, kind, title, ...})` + 正文席位 `ctx.slots.register({name:'sidebar.right.pane.tab'})`，与随包发布的"文件/浏览器/终端"走的是**同一条公开路径**；
- **Profile / 组合包**：`dsh-plugin-manager` 通过侧边栏"插件"页安装/启停，支持 `file:` 本地路径安装。

另外 `dsh-client-ui-sidebar-browser` 明确支持打开 **loopback 服务**——也就是现在这个 FastAPI（`127.0.0.1:8770`）可以不写一行代码，直接在右侧栏当一个 tab 打开。

### 三档形态

| 档 | 做法 | 工作量 | 得到什么 | 失去什么 |
|---|---|---|---|---|
| **L0 免开发** | 右侧栏浏览器 tab 打开现有 Web 应用 | 0 | 聊天与工具并排；agent 可直接用 bash/HTTP 驱动 | 无原生交互，仍是两套界面 |
| **L1 客户端插件** | 自写 tab，React 渲染候选/审核面板，调本地 API | 数天～1 周 | 原生观感；agent 与面板同会话；可做"选中即引用" | 需 Node/React 技术栈；构建需批准 |
| **L2 完整插件包** | Host 插件封装 Python 边车 + 注册工具 + 组合包分发 | 数周 | agent 具备 `harvest/verify/commit` 工具；subagent/workflow 扇出；可安装可分发 | 与 DSH 版本耦合；产品被绑在一个客户端上 |

### 对"workflow 灵活性"的实际增益
- 现在：我们的编排是**确定性流水线**（plan → 抓取 → 门卫 → 入库 → 分析），可复现、可审计；
- 接进 harness 后：可以按需**动态改查询、看结果再决定下一步、对可疑图开子 agent 交叉验证**——正好补第 2 节 ②③ 的短板；
- 但要注意张力：**loop 越自由，复现越难**。建议分工——*探索阶段交给 loop，落账阶段仍走确定性账本*（谁抓的、什么证据、哪一版，全部留痕）。

### 建议
产品面仍是**独立 Web 应用**（重做前端那件事不变，对外演示/评审需要链接）；DSH 侧边栏作为**分析师工作台叠加层**：
1. 先做 L0（今天就能验证值不值）；
2. 值，再做 L1（一个面板：候选车型 + 主图 + 通过/驳回 + 派发分析）；
3. L2 只在"内部批量跑 20 台车"这种场景才做，不做对外形态。

## 6. 建议的下一步（按性价比排序）

| 优先级 | 动作 | 预期收益 | 成本 |
|---|---|---|---|
| P0 | 通道健康度 + 熔断 + 结果缓存（同查询 24h 内复用） | 去掉重复请求与"假尝试" | 1 天 |
| P0 | 查询改写阶梯扩到 4 段（型号+类目 / 型号 / 品牌+构型 / 英文名），每段独立记诊断 | 召回提升，且可解释 | 1 天 |
| P1 | 把 `region_match` 实装：主图与参考图做局部匹配，产出 T1 证据 | 直接补"型号身份"缺口 | 3–5 天 |
| P1 | 候选图聚类（嵌入近邻）标"同款/异款簇"，混杂组自动告警 | 复现 T14 的构型混杂问题并前置拦截 | 3 天 |
| P2 | 出口策略（代理或错峰）+ 验证码转人工 | 通过率提升 | 视预算 |
| P2 | 官方/付费检索 API 评估（Bing/Serper/厂商开放数据） | 把"抓"变"取" | 1 周调研 |
| P3 | DSH L0 侧边栏试用 → 评估 L1 | 工作流灵活性 | 0 / 1 周 |
