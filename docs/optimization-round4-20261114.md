# 优化轮次 4：调研落地测试（Gleaning / 归一化去重）（2026-11-14）

## 0. 先回答：C（search_key）能不能现在就正式用

**能，而且已经默认在正式路径里**，但只以“兜底档”的形式：

- 触发条件：前三档（派生键 / 全名 / 别名）**全部 0 命中**；
- 代价：最多多一次图片搜索（约 1 次/目标），不会替换任何已命中的查询；
- 风险隔离：`query_tier="search_key"` 可统计触发率与效果；离线单测覆盖；
- 依据：25 样本里 3 个 0 命中案例 **3/3 救回**，其余情况不触发，因此对整体无副作用。

监控方式：看 `summary.delivery.query_tiers` 里 `search_key` 的占比，以及这些目标的核验通过率；
如果长期触发率极低（例如 <1%）且收益为 0，再考虑关闭。

## 1. R1：Gleaning 补抽（GraphRAG 做法）

**目的**：验证“同一批结果再问一轮‘你还漏了什么’”能否提升抽取召回（我们 60–126 条只抽 30–40%）。

**方法**：
- `plan_candidates --glean 1`：抽完第一轮后，把已抽车型列表拼回 prompt，再对**同一批结果**补抽一次；
- 5 份冻结 brief，全部运行（每份 8 条查询 × 2 次抽取）；
- 指标：新增候选数（`plan.glean.added`）、候选总数、新增候选的码覆盖。

**结果**：

| case | 候选数 | 补抽新增 |
|---|---:|---:|
| c1 | 18 | **0** |
| c2 | 22 | **0** |
| c3 | 26 | **0** |
| c4 | 25 | **0** |
| c5 | 36 | **0** |

**结论**：**不采纳**。在“标题 + 280 字摘要”这种输入上，第二轮没有新信息可抽；
GraphRAG 的收益来自**整篇文档**（长文本里确有漏抽实体），我们的输入是短摘要，前提不成立。
（代码保留 `--glean` 开关，默认 0，便于以后在“正文抓取”场景复测。）

**冲突**：与“抽取召回是瓶颈”的判断不冲突——瓶颈仍在，但解法不是补抽，而是**扩大输入**（正文）
或**结构化抽取**（槽位），见 §3。

## 2. R3-a：归一化 key 去重（GraphRAG / 商品匹配思路）

**目的**：验证“大小写/空格/标点/全角归一”能否补上现有规则去重漏掉的同款。

**方法**（离线，不联网）：对 96 份历史 plan / 2140 个候选，按归一化 key（NFKC、去空格/连字符/标点、
统一 ×）分组；同时检查当前合并簇里是否混入多个型号码，以及高 token 重叠但不同码的“模糊合并风险”。

**结果**：

| 指标 | 数值 | 说明 |
|---|---:|---|
| 存在重复组（归一后同名） | **19 组 / 15 份 plan**（0.9% 候选） | 例：`东方红LX2004` vs `东方红-LX2004`；多码拆分后同一长名重复 3 次 |
| 当前簇内含多个型号码 | **0** | 现有合并没有把不同码并掉（安全） |
| 高重叠但不同码（Jaccard≥0.8） | **1 对**（`XS143J` vs `XS143`） | 若用 RapidFuzz 式模糊合并会误并 |

**结论**：**部分采纳**。
- 归一化 key 能修掉 0.9% 的重复，成本极低，但收益也小；
- **不能**直接用它做“合并”：`东方红LX2004` 被判 generic、`东方红-LX2004` 被判 code，身份类型不同，
  强行归一合并会破坏“不同码不合并”的规则；
- 模糊合并（RapidFuzz 子集满分）会把 `XS143J` 和 `XS143` 并成一台——**必须保留型号码硬校验**；
- 真正该修的是**多码拆分的展示名**：拆成两条却保留同一长名，导致看起来重复；应改成“码 + 车系”的短名。
