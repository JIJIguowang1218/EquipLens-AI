# A/B 实验：无 skill vs 加载 association skill（2026-10-31）

| 属性 | 内容 |
|---|---|
| 目的 | 验证 `skills/association/` 是否真的提升"检索清单"的质量与可执行性 |
| 设计 | 2 arm × 8 个车型类别；每 arm 拆 2 个独立 subagent（互不共享上下文）各跑 4 例 |
| 判据 | 预注册于 `RUBRIC.md`：六维（口径/结构事实/部件轴/理由可审/必要确认/诚实度），格式项单列 |
| 隔离 | Arm A 禁读 `skills/`；两臂均禁读 `association-run-20261031.md` 与 `sample-association-list*`；均不联网 |
| 产出 | A：`armA-c01-04.md`、`armA-c05-08.md`；B：`armB-c01-04/*.json`、`armB-c05-08/*.json`；分数 `scores.json` |

## 0. 必须先声明的混淆（confound）

两臂都读了 `docs/roster-expansion-design.md` 与 `HANDOFF §3.2`——那是**这个模块自己的设计稿**，页槽、四轴阶梯、证据=图片都已写明。所以 Arm A 不是零信息基线，而是"**有设计思路、没有 skill 流程与校验**"的基线。这个偏差**抬高 A、压低两臂差异**，方向上对我们不利（保守估计）。

## 2. 三层结果（这才是结论）

### 2.1 判断质量：打平

两臂都指出了同样关键的判断：重型吊车名录吨位倒挂、XGC88000 履带吊无支腿、BJ5311JSQ 实为随车吊、"防护栏"三义、"支腿是作业状态件"；A 还额外挖出档案把「铲运机（scraper）」列为装载机别名这种数据错误。

**skill 没有让模型变得更聪明。**

### 2.2 合规性：B 明显更好

不越权、不编数字、缺口可解释、产物可机器校验；A 在 c03 违反了纪律（低置信档案仍给 9 个推荐）。

### 2.3 可用性：B 完全跑不动（最严重）

B 在 8 例里只填了 5 个页槽（5.2%）。按报告 20 页 / 12 个整车槽的口径，**B 的产物无法交付**；A 能填 92.7%，且把"待核/弱证据"标得清清楚楚。

## 3. 根因：这条纪律对冷启动类目是死结

`SKILL.md` 第 6 条 + `check_list` 实现的是「`grounding=inference` 未验证不得进推荐」。问题是：

- **方向级推断**（"沙漠环境用车可能提供防护栏证据"）天生就是假设，它必须**先跑名录生成**才能变成车型——这是正常工序；
- 但对没有档案/没有名录的类目（c03–c08 中的 6 例），**所有候选都是 inference**，于是推荐位恒为 0；
- 冷启动类目恰恰是这个模块的核心场景（T13–T15 定的"用户只给类目、EL 生成名录"规则）。

一句话：**我把"未验证"当成了"不可用"，实际上它只是"待验证"。**

A 的做法反而正确：给出"X 级"目标 + 标 `待核` + 附校准步骤，让流程能往下走。

## 4. 修正清单（skill v0.2）

| # | 问题 | 修法 | 优先级 |
|---|---|---|---|
| 1 | 方向级推断无法占槽 | 新增 `status=provisional`：方向级目标可占槽，但必须带 `verify_by`（如"名录生成"）；`recommended` 只给车型级已验证目标 | **P0** |
| 2 | schema 无 `profile_status` | 加字段（found/missing/draft），与 `textrun` 的 plan 对齐 | P1 |
| 3 | `slots.py` 不认语义门槛 | 去掉脚本的语义推断，只做算术；"谁进池"由模型给（B 已实测脚本会把 6×4 推上槽） | P1 |
| 4 | `check_list` 只有全阻断 | 改为 `blocking_scope: parts｜branches｜all` | P1 |
| 5 | `part_pages` 缺缺口原因 | 加 `why_not_ready` | P2 |
| 6 | `structural-facts` 全 pending 却要求"事实理由" | 加 `fact_status`，pending 时自动附确认项 | P2 |
| 7 | 部件专项页的槽位规则缺失（谁能占 `part:N`、阻断时怎么办） | schema 明确 part 槽分配规则，与 `vehicle:N` 分开校验 | P1 |
| 8 | `coverage` 无缺口类型枚举 | 加 `gap_kind: no_vehicle｜no_image｜no_roster｜undefined_scope`，替代自由文本 | P1 |
| 9 | schema 无 `confirmed_by` | 结构事实/排除项补 `confirmed_by` + `fact_status`，避免每条 exclude 都挂确认 | P2 |

补充观察（来自 Arm B 的执行记录）：

- **0.6 置信门槛把"薄档案"变成了"不能推荐"**：c05 装载机其实有档案（conf 0.55），仍被阻断式确认拦住。对一个以长尾类目为主的模块，0.6 这条线会把大多数类目判成"不可用"，与 `provisional` 缺失叠加放大成 0 推荐。
- **脚本与纪律的冲突已被实测两次**：c05 中 `slots.py` 会给 3 槽、c07 中会把公路自卸推上槽，B 都是"覆盖脚本 + 写 decisions"。这说明分配器只能做算术，语义门槛必须由模型持有（§4 第 3 条）。
- **B 的自我诊断与实验结论一致**：它明确写出"inference 永不占槽 + 无名录 ⇒ 这四个类目必然 0 推荐，清单退化为待验证候选包"。

## 5. 评分方法本身的缺陷（也要记下来）

预注册的六维**没有把"页槽填充率"作为一等指标**——它衡量判断质量，却不衡量交付性。结果出现"B 六维更高但交不出报告"的错位。这与"只测清单长得像不像人写的"是同一类错误。

**修法**：v0.2 的判据把 `fill_rate`（页槽填充率）与 `hard_errors` 并列为主指标，六维降为质量门槛（不达标一票否决）。

## 6. 结论

- 预注册判定：B 需 ≥ A + 0.5 且硬错误 ≤ A 一半 → B 6.000 vs A 5.875，**差值不达标**；硬错误达标。
- 判定：**判断质量无显著差异；合规性更好；可用性显著更差**。
- 因此 v0.1 **不应直接交付**。但结论不是"skill 无用"——B 补上 `provisional` 后有可能同时拿到"0 硬错误"和"90% 填充率"，这是下一次复跑要验证的唯一假设。

## 7. 下一步

1. 按 §4 改 skill v0.2（先做 P0 的 `provisional`）；
2. 用**同一批 8 例**复跑 Arm B（Arm A 结果作固定基线，不必重跑）；
3. 判据换成"fill_rate 主指标 + 六维门槛 + 硬错误"，看 B 能否 ≥85% 填充且 0 硬错误；
4. 若仍不行，说明约束化执行与冷启动交付天然冲突，应把"纪律"降到只保留 schema + 校验，把生成留给模型自由发挥。

## 9. v0.2 的结论：过线了，但是"名义填充"

**过线的部分**：`provisional` 这一档确实解开了死结——同样 8 个案例，B 从 5 槽提升到 82 槽，且 0 硬错误、8/8 过校验。方向级占槽 + `verify_by` + 转正路径写进 `decisions`，这个机制是对的。

**没过线的部分（指标被"撑满"）**：82 个槽里 **73 个是 provisional**（89%），真正确认到车型的只有 **9 槽（9.4%）**。也就是说：

> `fill_rate` 可以靠"12 个方向"填满，但报告里 12 页有 11 页的车型还没定。

这不是 B2 执行错——它在无档案/无名录的类目里没有别的选择；是**指标设计**的问题：v2 只测"槽有没有人占"，没测"占槽的东西是不是车型"。

## 10. 建议（v0.3 判据 + 模块行为）

**判据**：

| 指标 | 建议线 | 理由 |
|---|---|---|
| `fill_rate` | ≥0.85 | 页数交付底线（保留） |
| **`verified_rate`** = recommended 槽 / 12 | **单案例 ≥0.25，8 例均值 ≥0.3** | 防止"12 个方向"撑满；报告要能说清"这台车是谁" |
| `provisional` 占比 | 单案例 ≤0.6 | 超过就是没做取舍 |
| `hard_errors` / `schema` | 0 / 8-8 | 不变 |

按新线回看 B2：c01（3/12=0.25）、c02（0.17）、c03（0.08）、c05（0.25）勉强，其余 4 例为 0 → **均值 0.094，远低于 0.3**。所以 v0.2 仍然只是"规划脚手架"，不是"可交付清单"。

**模块行为**：下一步不该继续调 skill 文本，而应该**去补名录**——把 c06/c07/c08 的 `provisional` 用 `roster_generation` 转成 `recommended`，这是唯一能把 verified_rate 拉起来的动作。skill 侧只需把"每个 provisional 必须绑定一次名录生成任务"写成硬要求（`verify_by` 已具备，缺的是执行）。

## 12. 方法学反思：这两轮测的是"交付性"，不是"相关性"

**问题**：主指标 `fill_rate` 只回答"槽有没有被占"，不回答"选出来的车对不对"。更糟的是它能被 `provisional` 撑满（v0.2 的 82 槽中 73 槽是方向级）。`hard_errors` 只能挡住"明显错"，挡不住"平庸但合规"。

**已做过的相关性检查**（不够）：每个案例的 `must_have`/`must_not` 只是二值存在性检查（有没有出现环境轴、有没有排除履带吊），不是整体相关性排序，也没算 precision，更没负样本。

**正确的做法（v3 协议，复用已有 16 份清单，无需重跑）**：

1. **建池**：每案例取两 arm 目标并集 + 5 个应错的负样本（履带吊占支腿槽、公路自卸占矿用宽体槽、6×4 占沙漠牵引槽、载货车占随车吊支腿槽、乘用车底盘）。
2. **盲标**：混排随机编号，标 2（直证：同类目/同构型且部件可裁）/ 1（类比：异类目但能提供该部件或环境证据）/ 0（无关或结构错误）。
3. **指标**：

| 指标 | 定义 | 回答什么 |
|---|---|---|
| `precision@12` | 12 个推荐位中 label≥1 的比例（缺位计 0） | 选得对不对 |
| `nDCG@12` | 增益 `2^label − 1` | 对的是否排在前面 |
| 层覆盖 | exact/environment/platform 各至少 1 | "关联"这一层有没有做出来 |
| `wrong_type_rate` | 结构错误占比（必须 0） | 有没有硬错 |

4. **定位**：`fill_rate` 降为**可行性约束**（不达标一票否决），不参与 arm 间比较；`precision@12` 才是主指标。

**先行验证路径**：取 3 个案例（沙漠牵引车 / 重型吊车 / 压缩垃圾车）建池约 30–40 条，先出标注草案（2/1/0 + 一句理由），产品负责人抽查纠偏后计算 `precision@12` 与层覆盖。半天可出结论。
