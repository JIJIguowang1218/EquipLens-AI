# 关联分析预实验：模型判断 vs 预置数据表（2026-10-31）

| 属性 | 内容 |
|---|---|
| 目的 | 验证"关联分析由模型判断、不预置 部件→轴 表"是否可行；观察罕见类目会不会硬套 |
| 做法 | 对话模型扮演 planner（同 T18-pre，零 API 成本），按设计稿 §4 schema 输出清单提议并落账 |
| 输入 | ①沙漠牵引车＋踏步/防护栏/底盘 ②重型吊车＋支腿 ③随车吊＋支腿（档案低置信、未人工确认） |
| 数据依据 | `data/category_profiles.json`（沙漠牵引车 0.7；随车吊 0.4 未确认；**重型吊车缺失**）、`data-test/roster-*`（锁定名录） |
| 诚实边界 | 图库为空壳、图片不入仓 → 所有"主图/可裁"标 `to_verify`；**不编造库内素材数** |

字段约定（本实验新增两个，用于可审计）：

- `grounding`: `roster`（名录里查到的车型）/ `profile`（类目档案）/ `inference`（模型推断，必须验证）
- `needs_confirmation`: 模型认为不确定、需人确认的项（不是失败，是能力）

## 1. 沙漠牵引车 ＋ 踏步、防护栏、底盘

### 1.1 先发现的两个问题（都不是"表"能解决的）

1. **档案里的部件词表对不上请求**：`component_vocab` 是「前脸/大灯防护网/保险杠/遮阳板/后视镜/涂装」，用户要的踏步/防护栏/底盘**一个都不在**。若按档案词表生成查询，会去查"前脸"，直接答非所问。
2. **锁定名录里混着构型不符的车**：roster3 候选含 天锦、JH6、J6G、龙H5——这些是常规公路牵引车，不是 6x6 沙漠构型。名录"锁定"≠"构型正确"。

### 1.2 部件阶梯（每部件一条，轴按设计要求判定）

| 部件 | 设计逻辑（为什么是这样） | 阶梯 | 备注 |
|---|---|---|---|
| 踏步 | 防沙堆积、踏面防滑、离地高度适应沙地 | exact → **environment** → platform(重卡) → cross_vehicle(工程机械踏步) | 环境轴优先；平台轴只提供基型参照 |
| 防护栏 | 防沙板/侧防护、油箱与气瓶护罩、法规侧防护 | exact → **environment** → platform | 环境轴是主证据 |
| 底盘 | 离地间隙、油底壳/管路护板、进气防尘 | exact → **environment** → platform | 属"工程构型"证据（意见 #20 认可 P 档含工程构型），不是造型证据 |

对照：如果预置了 `部件→轴` 全表，第一条就会把"踏步"钉死在它曾在某个类目出现过的轴上；实际它在这个类目里是环境件。

| 2 | 豪沃 ZZ425 6x6 | 1 | exact | roster | 6x6 牵引底盘，防护与底盘处理有图解文（T18-roster 有 V/P 素材） | 0.8 |

## 2. 重型吊车 ＋ 支腿（档案缺失 → 走通用层 + 提议档案）

`data/category_profiles.json` **没有"重型吊车"**（只有"汽车起重机"）。这是设计里 `profile_missing` 的实盘场景：不许静默兜底，要显式标记并提议档案。

### 2.1 名录里发现的三处脏数据（比"表不够用"更值得注意）

`roster-重型吊车-20261018-163651.json` 12 个候选里：

| 候选 | 问题 | 对"支腿"的影响 |
|---|---|---|
| XGC88000 | **履带起重机，没有支腿** | 该目标对本部件无效，必须剔除 |
| BJ5311JSQ | **随车起重运输车**，不是重型吊车 | 恰好是 cross_vehicle 轴的证据（见下） |
| QY25K5C / QY35K5 / ZTC25 / XCT25 | 25–35 吨级，属**轻型/中型** | 与"重型"口径不符（T14 同类问题） |

结论：**"重型吊车"这个词本身就是口语类目**，无法直接当检索口径；必须先把它落到"吨位 + 底盘形式（汽车/全地面/履带）"两个参数上。这正是"规则系统覆盖不了"的地方——它不是长尾车型问题，是**类目词本身模糊**。

### 2.2 部件阶梯（支腿）

| 轴 | 说明 |
|---|---|
| exact | 重型吊车中"有支腿"的那些（汽车起重机/全地面起重机） |
| platform→ **cross_vehicle** | 支腿构型在大吨位与小吨位间可比（H 型/X 型、支腿盘、箱型截面）；随车吊支腿是现成参照 |
| 排除项 | **履带吊无支腿**——必须在"类目→可用部件"处硬排除（结构不存在，不是相关性弱） |

注意：这里"排除履带吊"不是相关性判断，是**结构事实**。它值得进数据（一次确认，长期有效），但不该写死成代码特判。

### 2.3 清单提议（8 推荐，其余待名录生成）

| 目标 | tier | 关系 | grounding | 理由 | 置信 |
|---|---|---|---|---|---|
| SAC16000S（三一 全地面） | 1 | exact | roster | 大吨位全地面，支腿是核心承力件，图解文多 | 0.7 |
| QAY 系列（徐工 全地面，吨位待定） | 1 | exact | inference | 全地面支腿构型典型；**具体型号需名录** | 0.5 |
| 中联 ZTC 系列（大吨位） | 1 | exact | roster | 同上 | 0.5 |
| 徐工 XCA 系列（全地面） | 1 | exact | inference | 大吨位全地面；型号需确认 | 0.4 |
| 随车吊支腿（BJ5311JSQ 等） | 3 | cross_vehicle | roster | 小吨位支腿构型参照；**标 borrowed** | 0.6 |
| 高空作业车支腿（蜘蛛式/剪叉） | 3 | cross_vehicle | profile(随车吊 adjacent) | 稳定支腿的另一条设计路线 | 0.4 |
| 履带吊（作对照，不取支腿） | — | exclude | roster | 明确写出"无支腿"，防止模型把履带吊当证据 | 0.9 |
| 重型清障车/救援车支腿 | 3 | cross_vehicle | inference | 作业稳定性需求相近；**验证样本** | 0.3 |

### 2.4 需要人确认

- "重型吊车"的吨位门槛（≥100t？≥200t？）——决定 tier1 收谁；
- 是否接受"随车吊支腿"作为类比证据（默认 `cross_vehicle` 需勾选）。

## 3. 随车吊 ＋ 支腿（档案低置信、未人工确认 → 检验"敢不敢说不知道"）

`随车吊` 档案：`confidence 0.4`、`confirmed_by: LLM-draft（待人工确认）`、`known_confusions: 常与汽车起重机/载货车混用`。

### 3.1 模型选择先说不知道

输出里必须先挂一个**阻断式确认**，而不是直接推荐：

```json
{"needs_confirmation": true, "blocking": true,
 "question": "随车吊要按哪种口径做？①起重为主（看支腿/吊臂，对标汽车起重机）②载货为主（看货厢/底盘，对标载货车）③两者都要",
 "why": "档案为 LLM 草案、置信 0.4；两类口径会得到完全不同的支腿证据"}
```

理由：支腿在"起重为主"里是核心承力件，在"载货为主"里是次要附件——口径不定，后面查什么都是错的。这是**敢说不知道**的正面案例。

### 3.2 确认后的阶梯（按"起重为主"假设）

| 轴上 | 内容 |
|---|---|
| exact | 随车吊 支腿（H 型、小吨位、与货厢共底盘） |
| platform | 汽车起重机支腿（同族大吨位，看箱型截面与支腿盘） |
| cross_vehicle | 高空作业车稳定支腿（另一种展开逻辑） |

### 3.3 清单提议（确认后，6 推荐 + 2 备选）

| 目标 | tier | 关系 | grounding | 理由 | 置信 |
|---|---|---|---|---|---|
| 程力 随车吊（蓝牌/黄牌待定） | 1 | exact | profile | 档案唯一代表车型；支腿与货厢共底盘，构型典型 | 0.6 |
| 徐工/三一 随车吊（吨位待定） | 1 | exact | inference | 主流品牌，图解文多；**型号需名录** | 0.5 |
| 随车吊 大吨位（8–16t） | 1 | exact | inference | 支腿跨度与箱型随吨位变化，是"构型差异"的对照组 | 0.4 |
| 汽车起重机（25–50t） | 2 | platform | profile | 同族支腿的成熟解法（borrowed） | 0.6 |
| 高空作业车稳定支腿 | 3 | cross_vehicle | profile | 展开逻辑不同，作对照（borrowed） | 0.4 |
| 载货车（无支腿对照） | — | exclude | profile | 明确"无支腿"，避免把货厢车当证据 | 0.7 |

## 4. 三个输入的横向对照：预置表会在哪里错

| 场景 | 预置 `部件→轴` 表会怎么错 | 模型判断怎么处理 |
|---|---|---|
| 踏步（沙漠车） | 表里"踏步"多半被归到"平台/功能件"（因为它在重卡里最常见） | 判"因环境而设计"→ 环境轴优先 |
| 支腿（重型吊车） | 表中若有"吊车→支腿"，会把 XGC88000 也拉进来 | 识别履带吊结构上无支腿，剔除 |
| 支腿（随车吊） | 表会直接给答案，跳过"类目口径"问题 | 先阻断问口径（起重/载货） |
| 重型吊车整体 | 表里没有这个类目 → 返回空 | 走通用层 + 提议档案 + 标 profile_missing |
| 名录制品的构型 | 表/名录都认为"命中即合格" | tier1 再判 6x6 vs 6x4、吨位与底盘形式 |

一句话：**表能记住"答案"，但答案依赖"这个类目、这个部件、这种口径"三个变量组合，表存不下，模型能现算。**

## 5. 这次跑出来的判断纪律（skill v0.1 的素材，不是事先写的）

1. 先问"这个部件是不是因环境/工况而设计"→ 是则环境轴优先于平台轴；
2. 结构上不存在的组合直接排除（履带吊无支腿；载货车无支腿），标注为事实而非相关性；
3. 类目词是口语时要落参数（吨位/底盘形式/上装），不能直接当检索口径；
4. 档案缺失 → `profile_missing` + 通用层 + 提议档案；档案低置信 → 阻断式确认；
5. 每条推荐必须写"能提供什么证据（可裁哪些部件/什么叙事）"，禁止写"相似"；
6. 宁可 `needs_confirmation` 也不猜；`grounding=inference` 的车型一律要经名录验证才能进正选。

## 6. 这次暴露的模型侧短板（必须由机制兜）

| 短板 | 现象 | 兜底 |
|---|---|---|
| 会编车型名 | 油田修井机、QAY/XCA 系列只给了系列没给型号 | `inference` 必须经名录生成验证；未验证不进正选 |
| 置信度自评不可靠 | 0.8 与 0.5 缺乏校准依据 | 置信只用于排序，不作为门槛；门槛用"是否 verified" |
| 不知道图 | 无法判断主图/可裁性 | 清单阶段一律 `to_verify`，进 M1 的图片粗判 |
| 倾向多给 | 容易把"军用越野""矿用宽体"都拉进来 | 页槽上限 + backlog 强制收敛 |

## 7. 结论

- **不预置 `部件→轴` 全表**：本次三个输入里，没有一个能靠一张表正确覆盖；且三个类目都需要"先判口径/先排结构不存在"。
- 需要固化的不是答案，而是 §5 的六条纪律 + `grounding`/`needs_confirmation` 两个字段。
- 值得进数据的只有**结构事实**（履带吊无支腿、载货车无支腿）和**已确认过的判断缓存**，且都必须带 `confirmed_by`。
- 下一步建议：把 §5 写成 skill v0.1 任务书，再用**未建档的第 4 个类目（高空作业车＋臂架）做盲测**，检验纪律是否可迁移。
