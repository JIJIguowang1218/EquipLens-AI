## 4. 轨迹（21 条事件，10.8 分钟）

```
BRIEF_READY
→ LIBRARY_SEARCH（库内 0，预期）
→ FETCH → VERIFY → FILL → GAP_CHECK
→ EXTERNAL_DISCOVER（exact：发现 12 个候选）
→ FETCH → VERIFY → FILL → GAP_CHECK
→ DEGRADE（exact 耗尽，开 environment）
→ EXTERNAL_DISCOVER（environment：12 个候选）
→ FETCH → VERIFY → FILL → GAP_CHECK（u-env 6/4 满，全局 6/12）
→ DEGRADE（全层耗尽）→ FAILED → WRITEBACK
```

预算消耗：24 queries / 24 models / 57 fetches / 57 verifies。

## 5. 两段式门卫在这一轮的角色

每张候选图都走了：

1. **第一段 `gate.prefilter`**：字节/解码/动图/长宽比/近空白/长边 <320 → 直接丢；
2. **第二段 `gate.check`（v4 标签集）**：keep/drop 竞争，`margin ≥ 0` 才放行；
3. **分层**：概览 ≥800、部件 ≥1200、参考层 <800；
4. **`RuleVerifier`**：标题含型号、构型一致、长边 ≥1200。

这一轮 20 张图通过 1+2+3，18 条同时通过 4（2 张被 `low_resolution` 拒在核验层）。这正是 loop 的 VERIFY 段在真实数据上的表现。

**证据落库是什么**：`image_evidence` 只存**元数据**（model / part / view / width / height / source_url / 证据等级 / 时间），**不存图片二进制**；图片另存在 `images/`。两者用 `asset_id`（URL 的 sha1 前 12 位）关联。

## 7. 结论

- ✅ **检索能力有底**：不靠任何历史数据，12 个候选里 6 台能凑齐 3 个部件的可用图；
- ✅ **loop 跑通**：发现 → 抓取 → 两段门卫 → 核验 → 填槽 → 缺口 → 降级 → 收口，全部有事件记录；
- ❌ **没到 12 槽**：缺口 6 台，原因是“名字检索不到同款图”+“低清”；
- ⚠️ **验收仍偏宽**：同一张图可以同时满足 3 个部件（没有部件可见性检查），真实“可裁”比例会更低。

## 8. 下一步

1. 把“名字 → 同款图”的召回做实：用型号代码/品牌官网图集，而不是 `"{model} 工程车"`；
2. 接部件可见性（P4 视觉），否则“6 台覆盖”是上限估计；
3. 扩源：经销商/二手页占了大半结果，需要官方/媒体源；
4. 证据库接回 `LIBRARY_SEARCH`，让第二次运行能从库里拿图。
