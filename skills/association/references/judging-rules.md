# 判断纪律与反例

先读反例，再写清单。**反例是约束，不是素材**——不要把它们当模板改写。

## 1. 先判"是否因环境/工况而设计"

- 正：同样一个"踏步"，在重卡里是平台继承件，在沙漠牵引车里是防沙、防滑、离地高度的环境件。
- **反例**：因为"踏步在重卡里最常见"就把它归到 platform 轴 → 于是去查常规重卡的踏步，答非所问。
- 判法：这个部件的形态**因工况而改变**吗？会 → environment 优先。

## 2. 结构上不存在的组合直接排除

- 正：履带吊没有支腿；载货车没有支腿。写成 `kind=exclude`、`status=blocked`，理由写事实。
- **反例**：因为"吊车都有支腿"把 XGC88000 拉进支腿清单 → 后续检索永远为空，浪费一个页槽。
- 注意：这类事实要**带 `confirmed_by`**，且只能当排除项，不能反向当推荐依据。

## 3. 类目词是口语时先落参数

- 正："重型吊车"→ 吨位（≥100t？）+ 底盘形式（汽车/全地面/履带）+ 上装。
- **反例**：直接拿"重型吊车"当检索口径 → 名录里混进 25 吨级和随车吊（T14/T18 实测）。
- 判法：这个词在行业里有没有多种落法？有 → 先给 `needs_confirmation` 或落参数。

## 4. 档案缺失/低置信要显式处理

- 正：`data/category_profiles.json` 没有该类别 → 标 `profile_missing`、走通用层、提议档案；置信 <0.6 或 `confirmed_by` 是 LLM 草案 → `needs_confirmation(blocking=true)`。
- **反例**：静默用通用层跑完，报告里却看不出"这个类目根本没有档案"。
- **反例**：把"随车吊"按"起重为主"直接做完，用户其实要的是载货为主 → 支腿证据全废。

## 5. 每条必须写"能提供什么证据"

- 正："防护栏——沙漠车的防沙板/侧防护构型，可裁前 45° 与侧视；提供环境特化证据。"
- **反例**："与目标车型相似""同系列""也是吊车"——这类理由无法复核，一律视为未写。
- 判法：把理由里的"相似"换成"它能给你看什么"。

## 6. 宁可 `needs_confirmation` 也不猜

- 正：模型不知道某系列的具体型号 → `grounding=inference`、`verified=false`，并写明验证途径（名录生成）。
- **反例**：编一个像模像样的型号名填进 `models`，看起来完整，实际不可检索。
- 判法：写完自查"这条我能不能指出出处？"不能 → 降级为待验证。
